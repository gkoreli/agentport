# Composition, inheritance, and the tier boundaries

> One of six independent reports from the 2026-08-20 survey. The findings are
> **frozen** — they describe the tree at `f7c8ee6`, and are not rewritten to
> flatter what shipped. The citations are NOT exempt from
> `npm run docs:check`: where a symbol has since moved, the citation is
> re-pointed at its current home and the original name kept in the prose, so
> the record stays true and the gate stays honest. What became of each
> finding is in `docs/research/README.md`.

# SUMMARY
The tier split is architecturally sound and mostly for the right reasons: `#trustedSurfaces` keying on delegation, the extension's ADR-009 name/alias withholding, the sessionStorage-vs-chrome.storage validation asymmetry (page-reachable storage validated exhaustively in `site/src/connect.ts#rememberedSession`, extension-only storage not, in `packages/extension/src/storage.ts#loadResume`), and `packages/extension/src/lifecycle.ts` extracting the reclaim rules as pure functions are all correct composition, not duplication. The genuine problem is a different shape: several *decision predicates* — not plumbing — exist as hand-maintained copies across tiers, and AGENTS.md's own rule ("a registry the compiler cannot check is a registry that will eventually be wrong") applies to every one. The gated-tool predicate is written seven times across five files, split between consent surfaces and enforcers; the terminal-resume-reason set that invariant 9 rests on is two string literal lists; the daemon's `#ask` and `#requestApproval` are the same tiered one-shot machine written twice and have already drifted (one grew a deadline, one did not); and `aguiStream`'s subscription set is not total over `SessionEvents`, which has already dropped `ask` on the floor with a live five-minute stall behind it. The seams themselves are good — `AgentRuntime`/`AcpRuntime` is a real adapter, `McpBridge` owns only the bearer boundary, `applyEvent` is the right boundary — but two abstractions are undercooked: `attachmentPolicy()` produces a policy whose justification names a destination while the routing to that destination lives in duplicated forks elsewhere, and `createWalletProvider` is a one-consumer abstraction the tier that should consume it explicitly refuses. Almost none of this needs the ADR-025 package split; that split is the right home for exactly one finding and a distraction for the rest.

## [P1/S] The "is this tool gated?" predicate is written seven times, and four of the copies are consent surfaces
`tool.requiresApproval || grant.alwaysAsk.includes(name)` is the single most decision-relevant fact on every consent screen — the line telling a user which lent tools will ask again — and it is independently re-implemented in seven files. Two are ENFORCERS (`packages/client/src/session.ts#AgentSession` in its tool-call path, `packages/daemon/src/daemon.ts#callTool`), five are DISPLAY (`packages/extension/src/consent.ts`, `wallet/src/app.ts` in `toolRows`, `examples/inkwell/src/app.ts#confirmGrant`, `packages/daemon/src/cli.ts`, `packages/daemon/src/connect-cli.ts`). The spellings already differ: `daemon.ts#callTool` tests truthiness in the pre-approval gate and `=== true` in the post-approval `browserApprovalRequired` recomputation; `wallet/src/app.ts` uses `=== true`; `examples/inkwell` uses truthiness. They agree today only because `requiresApproval` is `bool()` on the wire, so no falsy non-boolean can reach them. The failure mode is not a crash: it is a consent screen listing a tool as free while the enforcer gates it, or as gated while the enforcer does not — a user told the wrong thing about the one boundary they are being asked to authorize. Same class as the `SESSION_FRAME_TYPES` plain-`Set` bug, applied to a predicate instead of a registry.
EVIDENCE: packages/client/src/session.ts#AgentSession (tool-call approval branch), packages/daemon/src/daemon.ts#callTool, packages/daemon/src/cli.ts, packages/daemon/src/connect-cli.ts, packages/extension/src/consent.ts, wallet/src/app.ts (`toolRows`), examples/inkwell/src/app.ts#confirmGrant
RECOMMENDATION: Export one pure predicate from `@agentport/protocol` — it is pure, has no I/O, and both daemon and client already depend on that package: `isGated(tool: ToolDefinition, grant: Pick<CapabilityGrant,'alwaysAsk'>): boolean`, defined beside `TOOL_NAME_PATTERN` in `packages/protocol/src/limits.ts` or a new `grant.ts`. Replace all seven call sites in the same change, keeping no wrapper alongside (no-legacy tenet). Add a `wire:check` fixture asserting a grant whose `alwaysAsk` names a tool with `requiresApproval` absent is gated, and revert one call site once to watch it fail.

## [P1/M] `aguiStream` subscribes to a hand-picked list of session events; `ask` already fell out, and the local demo stalls five minutes because of it
`AguiAdapter`'s constructor registers eight listeners — delta, thought, plan, done, tool, approval, reattached, closed — and nothing in the type system says that list must be total over `keyof SessionEvents`. The ninth member, `ask`, is absent, and no AG-UI event or `agentport.*` CUSTOM event represents it, so `site/src/agentport-ui.ts#applyEvent` — the file AGENTS.md names as "the boundary" where richer transport events should land — is structurally unable to render a question. This is reachable today: `examples/inkwell/src/app.ts#attach` is a DIRECT-KEY attachment, so `#trustedSurfaces` returns `questions: true`, `AcpRuntime.openSession` declares `elicitation: {form:{}}`, claude-agent-acp therefore enables AskUserQuestion, the daemon sends the `ask` frame, `AgentSession#handle` emits it — and that demo has no `on('ask')` listener either. The turn then blocks for `ASK_TIMEOUT_MS` (five minutes) before decaying to a skip. Two tiers route questions properly (`packages/extension/src/sw.ts#askQuestion` to the consent window, `packages/daemon/src/daemon.ts#ask` to the terminal via `onLocalAsk`); the tier that consumes the adapter has no path at all, and the adapter is why nobody noticed.
EVIDENCE: packages/agui/src/index.ts (the `session.on(...)` list feeding `#off`), packages/client/src/session.ts#SessionEvents (`ask` member), site/src/agentport-ui.ts#applyEvent, examples/inkwell/src/app.ts#attach, packages/daemon/src/daemon.ts#ask (ASK_TIMEOUT_MS)
RECOMMENDATION: Make the subscription set compiler-total: build it from a `Record<keyof SessionEvents, (value) => void>` in `packages/agui/src/index.ts` so an omitted member is a type error, then delete one entry once to watch the build fail. Then decide `ask` explicitly rather than by omission — either an `AgentPortAskEvent` CUSTOM event (`agentport.ask`) that `site/src/agentport-ui.ts#applyEvent` renders as a form calling `session.answer()`, or a documented entry mapping it to nothing plus a log, which is honest only if the site tier can never receive one. Add `on('ask')` handling to `examples/inkwell/src/app.ts#attach`, the tier that can actually receive one today.

## [P1/S] Invariant 9's terminal-resume rule is two hand-maintained string lists in two tiers
AGENTS.md invariant 9 says "`revoked` is terminal for page and extension resume records; both clear the dead record rather than retrying withdrawn authority." That rule is enforced by the same four-element literal disjunction written twice — `not_resumable || grant_expired || authorization_expired || revoked` — in `site/src/connect.ts` (provider.resume) and `packages/extension/src/sw.ts#resumeFromStore`, with a third informal copy in the doc comment on `packages/client/src/wallet.ts#ResumeError`. The daemon mints these reasons and can grow a fifth; when it does, both tiers silently reclassify a dead session as transient and retry withdrawn authority on every page load and every worker restart — precisely the failure the invariant names — with no signal to either tier's author. The tiers legitimately differ in WHERE the record lives (sessionStorage vs `chrome.storage.session`) and how strictly it is validated on load; they do not legitimately differ in what "dead" means.
EVIDENCE: site/src/connect.ts (provider.resume error branch), packages/extension/src/sw.ts#resumeFromStore, packages/client/src/wallet.ts#ResumeError, packages/daemon/src/daemon.ts (the `session.denied` reasons)
RECOMMENDATION: Give `ResumeError` the answer: add a `terminal: boolean` getter (or an exported `TERMINAL_RESUME_REASONS` set) in `packages/client/src/wallet.ts`, derived from one union type shared with the daemon's denial reasons, and have both call sites read `err.terminal`. Files: `packages/client/src/wallet.ts`, `site/src/connect.ts`, `packages/extension/src/sw.ts`. Put the reason union in `@agentport/protocol` so a new daemon denial reason nobody classified is a compile error rather than a silently-transient one.

## [P1/M] `attachmentPolicy()` fixed the two-input problem but left the routing it justifies duplicated in two forks that have already drifted
The two-input redesign is right, and its own doc states the general rule: "a policy whose justification names a destination must be produced by the same code that routes there." The code does not yet obey it. `#trustedSurfaces` computes `decisions`/`questions` by testing whether `onLocalApproval`/`onLocalAsk` exist; `#ask` and `#requestApproval` then each re-derive the same fork (`if (session.viaConnect) { const h = this.#options.onLocalX; if (!h) return <refuse>; ... }`), each carrying a comment calling that branch "a second lock on the same door." A second lock is the tell: the destination is re-decided at the point of use instead of carried. The two are otherwise the same one-shot machine — register a deferred in a session map before the frame leaves, use `map.delete()`'s boolean as the single-winner interlock, wire abort, clean up in `finally` — and they have drifted the way duplication predicts: `#ask` carries `ASK_TIMEOUT_MS` on both local and wire paths, while `#requestApproval`'s wire path has no deadline at all and relies solely on the turn's abort signal. A browser wallet that accepts an `approval.request` and never answers blocks the agent's turn until a human cancels; "never hang" holds for questions and not for decisions, for no stated reason.
EVIDENCE: packages/daemon/src/runtime.ts#attachmentPolicy, packages/daemon/src/daemon.ts#trustedSurfaces, packages/daemon/src/daemon.ts#ask (ASK_TIMEOUT_MS), packages/daemon/src/daemon.ts#requestApproval (no timer), scripts/e2e.ts (the `attachmentPolicy({decisions,questions})` fixture)
RECOMMENDATION: Introduce an internal `ConsentRouting` object in `packages/daemon/src/daemon.ts` holding the two resolved destinations (`decisions`, `questions`, each already bound to the terminal handler or to this session's wire path), and have `attachmentPolicy(routing)` derive `{mayAsk, mayUseOwnTools}` from whether each is non-null. `#ask`/`#requestApproval` then invoke the surface they were handed, and both `viaConnect` forks plus both "second lock" branches become unrepresentable. Keep `AttachmentPolicy` a pure data object — it crosses into `AgentRuntime.openSession` and `AcpRuntime` reads `policy.mayAsk === true`; putting callables on the object handed to a runtime would let a runtime reach a consent surface directly, which is the boundary the daemon exists to hold. Give the shared one-shot helper a required deadline parameter so `#requestApproval` cannot ship without one.

## [P1/S] The extension boundary re-states protocol bounds and degrades silently where the drop-in tier fails loudly
`packages/extension/src/bridge.ts` imports `MAX_PLAN_STEPS`, `MAX_FORM_FIELDS`, `MAX_ANSWER_CHARS`, `MAX_FORM_LABEL_CHARS` from the protocol — then hand-copies four more bounds into its own `LIMITS`: `tools: 64` (= `MAX_TOOLS_PER_GRANT`), `toolNameLength: 128` (= `MAX_NAME_CHARS`), `descriptionLength: 4096` (= `MAX_DESCRIPTION_CHARS`), `textLength: 128*1024` (= `MAX_TEXT_CHARS`). They agree today, which is exactly the condition AGENTS.md warns about, and `packages/protocol/src/limits.ts` is documented as the one place a bound changes. The behavioural consequence is visible without any drift: `sanitizeToolDefinition` responds to an over-long description with `?? name`, so the tool's DESCRIPTION silently becomes its NAME — the text a user reads on the consent card — and `sanitizeTools` drops a tool with an over-long or non-matching name entirely, so a site that lends four tools attaches with three and is never told. The same site code on the drop-in tier hits `packages/client/src/wallet.ts#buildGrant`, which throws a message written for a developer to act on. One integration, two failure semantics, and the quiet one is on the tier the north star calls the widest form of the product. The inline tool-name regex in `sanitizeToolDefinition` is also a third spelling of `TOOL_NAME_PATTERN`.
EVIDENCE: packages/extension/src/bridge.ts (`LIMITS`, `sanitizeToolDefinition`, `sanitizeTools`), packages/protocol/src/limits.ts (MAX_TOOLS_PER_GRANT, MAX_NAME_CHARS, MAX_DESCRIPTION_CHARS, MAX_TEXT_CHARS, TOOL_NAME_PATTERN), packages/client/src/wallet.ts#buildGrant, packages/client/src/wallet.ts (explainGrantViolation)
RECOMMENDATION: Delete the four duplicated `LIMITS` members in `packages/extension/src/bridge.ts` and import them from `@agentport/protocol`; keep only the genuinely extension-local ones (`sessionsPerChannel`, `pendingCallsPerSession`, `jsonBytes`), which have no wire meaning. Reuse `TOOL_NAME_PATTERN` instead of the inline regex. Then make the degradation visible: `sanitizeTools` should report dropped names alongside accepted ones, and `packages/extension/src/sw.ts#openSession` should surface that to the consent window and to the page's `err` reason — a site whose lent tool the agent will never see must be told, on the same grounds as `ownTools`.

## [P2/M] Three hand-written projections of the same agent stream into the same chat store, and one has drifted
`src/nisli-ui/lib/chat.ts` is the protocol-neutral store both surfaces target, so the projection into `ChatUpdate` is the shared piece — and it exists three times over. `site/src/agentport-ui.ts#applyEvent` folds AG-UI events; content.ts's `onWidgetEvent` (since moved to `packages/extension/src/widget.ts#event`) folds raw session events by hand (delta → `message.start`/`message.delta`, thought → `reasoning.*` under a `${promptId}:reasoning` id, tool → `tool.start`/`tool.end`, done → `run.end`/`run.error`), duplicating bookkeeping `packages/agui/src/index.ts` already owns; and the history replay is written again in `site/src/agentport-ui.ts#seed` and content.ts's `rehydrateWidget` (since moved to `packages/extension/src/widget.ts#rehydrate`) as near-identical loops over `HistoryEntry.role` minting `history-${seq}` ids. The drift is already in the source: the comment in `content.ts#onWidgetEvent` states "the site panel keeps a finished plan on screen; that is a bug there" — but `applyEvent` clears `plan.value` on `RUN_FINISHED`, `RUN_ERROR` and `agentport.reattached`. One copy is now documented against a behaviour the other no longer has. Note the real constraint: `@agentport/agui` pulls in zod and is deliberately kept out of `connect.js`, so "just use aguiStream in the content script" is not automatically right.
EVIDENCE: site/src/agentport-ui.ts#applyEvent, site/src/agentport-ui.ts#seed, packages/extension/src/widget.ts#event (then content.ts#onWidgetEvent), packages/extension/src/widget.ts#rehydrate (then content.ts#rehydrateWidget), packages/agui/src/index.ts (#onDelta/#onThought/#onTool/#onDone), src/nisli-ui/lib/chat.ts
RECOMMENDATION: Extract the dependency-free half first: `historyToChatUpdates(entries: HistoryEntry[]): ChatUpdate[]` beside `src/nisli-ui/lib/chat.ts`, consumed by both `#seed` and `#rehydrate` — identical in both, pure, and testable under happy-dom in `scripts/ui-smoke.ts`. Then extract the streaming fold as a second pure reducer over the semantic `SessionEvents` shapes (not AG-UI types, so the content script pays no zod cost) and have `applyEvent` call it for the events needing no AG-UI-specific handling. Delete the stale plan comment in `content.ts` in the same change.

## [P2/S] `createWalletProvider` / `WalletUi` is an abstraction with one consumer that the tier it was designed for explicitly refuses
`packages/client/src/provider.ts` exports `createWalletProvider`, `WalletUi` and `ProviderRejected`. The only consumer is `examples/inkwell/src/app.ts`. The service worker — the real wallet, and the natural consumer — declines it in a comment: "Deliberately not `createWalletProvider`: that helper builds the surface descriptor without an origin, which would let the agent see the extension's own origin." `site/src/connect.ts` does not use it either. Meanwhile `packages/extension/src/inpage.ts` hand-writes both halves of what `provider.ts` offers: its own `ProviderRejected` class with a comment saying "Rejection reasons match `ProviderRejected` in @agentport/client", and its own `navigator.agent` definition with a comment saying "Mirrors `installProvider`". A structural claim maintained by two comments is a shape this repo has paid for before. By the dogfooding tenet this is decoration; ADR-025 R2 already schedules `createWalletProvider` for deletion and `installProvider` for extraction into a provider-author subpath dogfooded by the extension — but that ADR is proposed and its package split unimplemented, so nothing has moved.
EVIDENCE: packages/client/src/provider.ts#createWalletProvider, packages/client/src/provider.ts#WalletUi, packages/client/src/provider.ts#installProvider, packages/extension/src/sw.ts#openSession (the refusal comment), packages/extension/src/inpage.ts (local `ProviderRejected`, the `Object.defineProperty(navigator,'agent')` block), examples/inkwell/src/app.ts, docs/ADR-025-custody-safe-client-boundary.md R2
RECOMMENDATION: Do not wait for the package split for the cheap half. Make the rejection-reason union one exported type in `@agentport/client` and have `packages/extension/src/inpage.ts` plus `packages/extension/src/bridge.ts#ExtensionProviderErrorReason` reference it instead of restating it, so the two comments become a type. Give `installProvider` an optional origin so `inpage.ts` can call it rather than mirror it. Delete `createWalletProvider`/`WalletUi`, inlining the twenty lines `examples/inkwell` uses — a helper whose only caller is a demo is the demo's code, not a library's.

## [P2/M] `PageSession` and `AgentSession` implement the same handle contract twice, including a hand-rolled emitter next to an available one
`packages/extension/src/inpage.ts#PageSession` and `packages/client/src/session.ts#AgentSession` both implement `AgentSessionHandle`, and both independently implement: the in-flight-turn set and its rejection on close, the `#closed` flag and `finish(reason)` semantics, `prompt` delegating to `startPrompt`, `answer`'s skip-vs-answered branch, and a listener registry. `AgentSession` extends `Emitter` from `@agentport/protocol` — isomorphic, dependency-free, already imported by page-world code; `PageSession` hand-rolls `#listeners` plus its own `emit`. The bound checks in `PageSession.answer` are duplicated deliberately and correctly (ergonomics on the untrusted side, with the authoritative copy in `sanitizeAnswerFields`), and the `info` type divergence is correct too (ADR-009 withholds the real agent name from the page). What is not justified is two implementations of turn bookkeeping and two emitters. This is also the one place where inheritance would be the honest modelling choice rather than ceremony — one public contract over two transports with genuinely shared lifecycle state — but the cheaper and equally correct move is composition, so I would not reach for the base class first.
EVIDENCE: packages/extension/src/inpage.ts#PageSession (`#listeners`, `#turns`, `finish`, `emit`), packages/client/src/session.ts#AgentSession (`#transcripts`, `#finish`), packages/client/src/session.ts#AgentSessionHandle, packages/protocol (Emitter)
RECOMMENDATION: Have `PageSession` extend `Emitter<SessionEvents>` from `@agentport/protocol` and delete `#listeners`/`emit`/`on` — this alone removes the duplicated registry and makes both tiers deliver events with identical semantics (listener snapshotting, unsubscribe). Then extract the turn bookkeeping (`#turns`/`#closed`/`finish`) into a small `TurnBook` helper in `@agentport/client` used by both classes. Only a third handle (a future controller or a native provider) would earn an abstract base; two does not.

## [P2/S] McpBridge is a clean seam, but AcpRuntime mints it a private random id, so the one boundary where site tools reach the agent cannot be correlated in logs
`McpBridge` is a good composition seam: it owns the bearer boundary and the `mcpToolName` mapping and nothing else, delegating framing, schema validation and cancellation to the official SDK. `AgentRuntime`/`AcpRuntime` is a good adapter too — the ACP-to-AgentPort mapping is nearly one-to-one and `AGENTPORT_ACP_COMMAND`/`ARGS` genuinely make it pluggable. Two seam defects sit inside otherwise-good code. First, `AcpRuntime.openSession` sets `#bridgeSessionId = 's_' + Math.random().toString(36).slice(2,12)` — a fourth id-minting convention, ignoring `randomId` from `@agentport/protocol`, and unrelated to the AgentPort session id, so every `McpBridge` log line (`MCP tool call started/completed/failed`, naming the tool the site lent) carries a `sessionId` appearing in no other log in the system; the daemon's tool-dispatch log and the bridge's invocation log for the same call cannot be joined. Second, `AcpRuntime.openSession` re-declares its parameter structurally instead of using `AgentRuntime['openSession']`'s type; because TypeScript checks method parameters bivariantly, adding a field to the openSession context will not fail this class, so a runtime can silently stop receiving something the daemon now passes.
EVIDENCE: packages/daemon/src/runtimes/acp.ts#AcpRuntime (`#bridgeSessionId` assignment inside `openSession`, and `openSession`'s inline parameter type), packages/daemon/src/mcp-bridge.ts#McpBridge (`register`, `#installHandlers` logging), packages/daemon/src/runtime.ts#AgentRuntime, packages/protocol (randomId)
RECOMMENDATION: Pass the AgentPort session id through the openSession context and use it as the bridge registration key in `packages/daemon/src/runtimes/acp.ts` — `McpBridge.register` already hex-encodes the key for the URL path, so a wire session id is safe there. Declare `AcpRuntime.openSession(context: Parameters<NonNullable<AgentRuntime['openSession']>>[0])` so an interface change breaks this class. Both are small and both restore properties the seam was meant to have.

## [P3/S] The WebMCP belief is correctly centralised, but the merge rule deciding which tool wins is copied into both harvesters
`packages/client/src/webmcp.ts` is the model for how this codebase should hold a shared belief — one artifact, `WEBMCP` and `WEBMCP_NOT_IMPLEMENTED` as the machine-readable and negative halves, both harvesters explicitly demoted to "wiring", and the file records that two copies is exactly how both harvesters ended up wrapping `provideContext()` five months after the draft removed it. One rule escaped it. "Explicit tools win a name collision over harvested ones" is a policy about which handler the agent actually reaches, and it is implemented twice: `site/src/webmcp.ts#createWebMcpHarvester` (the `harvest` closure) and `packages/extension/src/inpage.ts#mergeWebMcpTools`, as the same seven-line Map fold. They agree today. If they ever disagree, the same page lends the agent a different implementation of the same tool name depending on which tier the visitor is on, and nothing would report it.
EVIDENCE: packages/client/src/webmcp.ts (WEBMCP, WEBMCP_NOT_IMPLEMENTED, createWebMcpRegistry), site/src/webmcp.ts#createWebMcpHarvester, packages/extension/src/inpage.ts#mergeWebMcpTools, scripts/webmcp-harvest.ts
RECOMMENDATION: Add `merge(explicit: readonly SiteTool[]): SiteTool[]` to the registry returned by `createWebMcpRegistry` in `packages/client/src/webmcp.ts`, and have both `site/src/webmcp.ts#createWebMcpHarvester` and `packages/extension/src/inpage.ts#mergeWebMcpTools` call it. `scripts/webmcp-harvest.ts` already asserts the collision rule ('an explicit tool keeps its own gating'), so that check moves from covering one harvester to covering the rule both use.
