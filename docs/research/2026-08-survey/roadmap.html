AgentPort Roadmap

Architecture, capabilities, integrations, and product sequence — synthesized from a six-agent fan-out over the repo, the deployed artifacts, and the August 2026 landscape.

2026-08-20 · main = v0.1.7 + 1 CI commit · protocol agentport/6 · deployed bundle verified byte-identical to main

The verdict in four sentences. The engineering is far ahead of the product: 45 validated frames, sealed sessions, a real ACP runtime — and zero third-party integrations, a front door broken in two places right now, and the one capability nobody else has (the generic page harness) locked behind an unlisted extension. The architecture needs no grand redesign; it needs its domain entities to own their rules — the same extraction pattern revocations.ts and lifecycle.ts already prove — because every drifted duplicate found is a rule written twice. The landscape moved decisively this month: WebMCP tool supply arrived at platform scale (Cloudflare edge-injection Aug 6, Shopify storefronts reported Aug 5) with no demand-side consumer yet — and AgentPort is a demand-side product. The window is a distribution race: the wedge is the extension harness, and the Chrome Web Store listing is engineering, not a release decision.

0 · Fix the front door this week

The vision agent walked the deployed paths as a stranger and found requirement 6 broken for the third time — both instances are small and both sit on the only two paths a stranger walks:

P0The CLI's first printed link is a dead page

packages/cli/src/main.ts#defaults points every stranger at the hosted /pair, which is deliberately script-free and says only "Waiting for the AgentPort extension…" — an extension with no store listing. The working path (the hosted wallet's Pair tab, which already reads #code=) is never mentioned. Fix: a static fallback paragraph on pair.html linking the wallet, and the daemon's pairing print names both routes.

P0The live landing hero snippet throws before it reaches the network

Its alwaysAsk names a tool absent from tools, so buildGrant rejects it for anyone who copies it verbatim; it also omits data-relay/data-wallet, so it dials the adopter's own origin. Fix: use the README snippet, and add the check the north star predicts — extract the snippet from the page, serve it from a foreign origin, and assert connect() reaches a relay dial. An artifact property, not a belief about visitors.

P1The default runtime fails opaquely on unauthenticated machines

Nothing documents the Claude Code prerequisite; AcpRuntime never reads authMethods or calls ACP authenticate, so failure arrives in the browser minutes later. Fix: agentport doctor (spawn the resolved ACP pair, complete initialize, report capabilities, exit non-zero with the remediation), run implicitly before the first pairing code. Document AGENTPORT_AGENT_CWD — the highest-consequence undocumented variable in the project.

1 · Architecture: entities should own their rules

The DDD audit's conclusion is precise: the protocol models entities well as shapes (schemas with inferred types), but almost none own their rules — the rules live as inline boolean conjunctions inside four host classes, copy-pasted wherever a second party judges the same entity. Every duplicate found has already drifted or already hurt. The fix is not a framework; it's the extraction pattern the repo has proven three times (revocations.ts, lifecycle.ts, webmcp.ts).

P0SessionDelegation validity is written three times and has drifted

Relay, daemon, and connect.ts each hand-write the conjunction — different clause sets, a dead clause the schema makes unreachable, a hand-rolled regex beside the exported validator, and no judge checks issuedAt against the clock, so a future-dated delegation survives a revocation tombstone recorded now. One browser-safe delegationAuthorizes() predicate in the protocol package, with a closed reason set, called by all three.

P0Live revocation is a caller obligation, and it misses the extension tier entirely

Two findings converged here. AgentDaemon#enforceRevocations is only ever called by a setInterval in cli.ts — any other embedder gets tombstones honoured at open and never during live traffic. Worse: every revocation check sits inside a delegation guard, and the extension opens direct-key sessions with no delegation — so agentport revoke <origin> writes a tombstone, logs, and leaves the extension attachment alive and reopenable. A false guarantee on north-star requirement 4, and the hard prerequisite for remembered consent. Fix: an AttachmentAuthority value object (expiry + revocation + allows(tool) in one place), tombstones keyed on the attachment's origin rather than the delegation, and the sweep moved into the daemon's own heartbeat.

P1Three more predicates that need one home

Tool gating — requiresApproval || alwaysAsk.includes(name) is spelled out in seven files, four of which draw consent screens; a divergence under-warns the user on the exact boundary they're authorizing. Export isGated() from the protocol. Terminal resume denials — invariant 9 rests on two hand-copied string lists; a fifth daemon reason would make both tiers retry withdrawn authority forever. Make it a protocol vocabulary. The AG-UI subscription set — not compiler-total over SessionEvents; ask already fell out, so the inkwell demo blocks five minutes on an agent question no surface renders. Make the set a Record<keyof SessionEvents, …> so omission is a type error, then handle ask deliberately.

P1attachmentPolicy should be derived from routing, not asserted beside it

The two-input redesign was right, but #ask/#requestApproval still re-derive the viaConnect fork the policy claims to describe — and they've drifted: #ask has a deadline, #requestApproval waits forever on a silent wallet. Build one ConsentRouting object at session open with the destinations already bound, derive the policy booleans from it, and give the shared one-shot helper a required deadline so an approval cannot ship without one.

2 · Capabilities: what the wire cannot say yet

The protocol expresses the whole conversational loop. What it cannot express is state changing under the session — and that single theme gates both north-star demands. Three items justify the next lockstep cutover (protocol v7); batch them with the runtime-redaction fix so one cutover pays for all four.

P0The grant is frozen at attach — add grant.update

No frame updates a live grant, so WebMCP's toolchange has no channel, same-origin navigation leaves the daemon believing the old document's tools, and reclaimKeyFor must refuse to carry WebMCP widgets across navigations at all. The security design is the hard half and must be asymmetric: narrowing needs nothing; widening requires a fresh delegation whose grantHash covers the new grant — anything else lets a page grow its own authority mid-session. Highest-leverage frame the protocol lacks.

P0Content blocks: everything is text, in both directions

No image, no attachment, no resource link anywhere in 45 frames — "look at this" is the first thing users try. ACP already handles content blocks, so the runtime side is nearly free. Build the upload direction only; the download direction moves the agent's own data into a site and must ride runtime_own_tool authority, or it's the exfiltration path ADR-021 §6 warns about wearing a new field name.

P0The context fields are a shipped no-op — cheapest fix on this list

SurfaceDescriptor.context and Prompt.context are validated, sealed, routed, delivered — and never read by the daemon. The reference site passes both. Thread them into the ACP preamble under the existing untrusted-data framing, and add the e2e assertion so it can't rot back.

P1One agent everywhere is currently N agents wearing one name

Each attachment spawns a fresh ACP process with a fresh conversation — the exact opposite of the north-star signal, and unbounded (N attachments = N model processes). ACP supports multiple sessions per connection; hoist the process to daemon lifetime, keep the AgentPort session as the authority unit (McpBridge already isolates tools per session, which is what makes this safe). Ship a concurrency cap first so today's behaviour degrades honestly. Related: either narrow the "with your memory" wording, or build opt-in conversation continuity via loadSession — decided at the daemon, never by the page.

P1Detach kills the turn; nothing can tell the user when work finishes

"Ask your agent the long thing, come back later" is structurally impossible: detach aborts the prompt controller outright. Split the blanket rule — keep the turn alive, fail tool calls fast with client_detached. Notification belongs in the extension service worker and the daemon's local surface, never the relay (it would be the first durable state the relay ever held).

P1Revocation exists but is unreachable; and the agent key is a supercookie

No surface lists what currently holds your agent — the data all exists in the extension's session table and cert store; add the popup view with per-row revoke and a kill-all. Separately, every site learns the stable agent public key — a cross-origin correlator that ADR-009 already named blocking. Pairwise per-origin identity (HKDF over device key + origin) needs its own ADR before the extension is distributed; identifier schemes can't be changed after sites depend on them.

P1Harness verbs: the missing four, in consent-risk order

page.waitFor and page.find are pure reads — build now (and make page.scroll await settle; today a scroll-then-read returns the pre-scroll DOM). page.select/setChecked/pressKey are mutations and must land after the approval card can name its target — today the card says Run page.click {"element":"g3e12"}, which trains reflexive approval, the worst outcome ADR-021 names. page.navigate needs the cross-origin decision and its own authority domain. Also: the harness reports shadow-DOM/iframe blindness as an empty page rather than an unreadable one — count what was skipped and say so; and the obstruction check treats "couldn't look" as "clear" on every below-the-fold click — make it three-state.

3 · Integrations: the month the supply arrived

Between May and August the landscape moved decisively on the half of the thesis AgentPort does not own — site-declared tools — and barely at all on the half it does own: no browser or OS vendor lets a user supply their own remote agent. Verified as of this week:

  • WebMCP is a W3C CG draft (2026-08-19) in a Chrome origin trial from 149; the API moved to document.modelContext.registerTool(tool, {exposedTo, signal}) with toolchange and a declarative form variant. Cloudflare ships edge-injected WebMCP for any fronted site (Aug 6); Shopify reportedly enabled it across Liquid storefronts (Aug 5). Supply at platform scale, no mainstream consumer yet.
  • MCP 2026-07-28 is the largest breaking revision ever: handshake removed, server/discover mandatory, MRTR replaces server-initiated elicitation. McpBridge targets the old shape — and MRTR is genuinely a better fit for the approval round-trip (authority re-judged on the retry, carried in requestState).
  • ACP hit 1.0–1.6 with 60+ agents and 13 clients; an Active RFD standardizes ACP over WebSocket/HTTP while explicitly deferring origin validation, version binding, and the security audit — the exact problems AgentPort has already solved and adversarially tested.
  • Claude in Chrome went GA — the closest competitor to the widest-form claim, but local-only (native messaging), single-vendor, and the site is not a party. The nearest direct competitor (WebMCP Bridge) has 178 users. The shelf is empty.

4 · Product: the wedge and the race

There are exactly two integrations in existence, both toys, both ours. The script-tag story asks a site to ship a feature serving zero of its visitors — an unwinnable cold start (the Payment-Handler postmortem in the prior-art review says exactly this). The wedge is the thing no site and no browser vendor can supply: the user's own remote agent, with their files and MCP servers, acting on any page through the extension harness. That creates the user population that makes the site-side proposition ("an assistant with no inference bill and no SDK") real later.

Distribution is engineering, and the repo's own note claiming otherwise is false. The manifest's broad host permissions are load-bearing but trigger the store's heaviest review; between here and a listing: a privacy policy and permission justification as source-controlled files, passkey wrapping for the root key (currently plaintext hex — gate the listing on this), the revocation UI, per-origin enablement (today the extension announces itself on every page on the web before any consent — a fingerprinting bit that contradicts the north star verbatim), the unconditional keep-alive alarm fix, and release builds without inline sourcemaps. This gates adoption signals 2, 5, and 6 — the highest-leverage large item in the plan.

Two cheap truth-fixes that make walked signals report the right answer: refresh identity labels (runtime/name/location) from env on every load — today a goose swap keeps a cert stamped claude-code; and carry the relay URL on stored certs so one user can hold agents on two relays. And one honesty item for the next cutover: the daemon still tells every page which runtime the user runs — first entry on the "site learns nothing" list, enforced today by asking integrators nicely.
