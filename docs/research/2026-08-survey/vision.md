# Product vision — what a stranger actually meets

> One of six independent reports from the 2026-08-20 survey. The findings are
> **frozen** — they describe the tree at `f7c8ee6`, and are not rewritten to
> flatter what shipped. The citations are NOT exempt from
> `npm run docs:check`: where a symbol has since moved, the citation is
> re-pointed at its current home and the original name kept in the prose, so
> the record stays true and the gate stays honest. What became of each
> finding is in `docs/research/README.md`.

# SUMMARY
Deployed and main are effectively the same system right now — the hosted `connect.js` is byte-identical to `site/public/connect.js` (sha 7d0cfd74…), both speak `agentport/6`, and only one CI-only commit sits after tag `v0.1.7` — so "landed is not shipped" is not the current problem. The current problem is that the front door is broken for the third time, in the same class the north star's own postmortems describe: the published CLI's default `AGENTPORT_WALLET` points every stranger at `https://agentport.gogakoreli.workers.dev/pair`, which is a script-free page reading "Waiting for the AgentPort extension…" that can only ever be driven by an extension with no store listing, and the live landing page's hero snippet throws before it reaches the network because its `alwaysAsk` names a tool absent from `tools`. Both are minutes of work and both sit on the only two paths a stranger walks. Underneath that, the engineering is genuinely strong and far ahead of the product: 45 validated frames, sealed sessions, a real ACP runtime, revocation, resume, a hosted-wallet tier and an extension harness — but there are zero third-party integrations, two toy demo surfaces authored in-house, no preflight for the default runtime's undeclared Claude Code dependency, and the one capability nobody else can copy (the extension's generic `page.*` harness on sites that declared nothing) is locked behind a distribution step that is misclassified as "not engineering." The wedge is not the script tag; it is the extension harness, and everything below sequences toward making that installable and worth installing.

## [P0/S] MOVE 1 — The published CLI's first printed link is a dead page for every stranger
`packages/cli/src/main.ts#defaults` sets `AGENTPORT_WALLET ??= 'https://agentport.gogakoreli.workers.dev/pair'`, and `packages/daemon/src/cli.ts`'s `onPairingCode` handler prints that URL with `#code=` as the headline instruction: "Your agent is ready to pair:". The deployed `/pair` (verified by fetching it) contains no `<script>` at all — deliberately, because the page must not be able to sign — and its only text is "Waiting for the AgentPort extension…". The sole thing that can advance it is `packages/extension/src/content.ts`, which gates on `location.pathname === '/pair'`, and that extension has no Chrome Web Store listing. So the single command that the README, the npm page, the CLI README and the landing page all tell a stranger to run terminates in a page that hangs forever, with no explanation, no alternative and no link. The working path exists — the hosted wallet's Pair tab — but nothing tells the user it exists, and the daemon never mentions it. This is the exact requirement-6 failure class the north star documents twice, now on its third instance.
EVIDENCE: `packages/cli/src/main.ts#defaults`; `packages/daemon/src/cli.ts` `onPairingCode`; `site/public/pair.html` (`#pair-status`, no script, deployed copy identical); `packages/extension/src/content.ts` `/pair` pathname gate; `wallet/src/app.ts` `pairCode` already reads `code` from `location.hash`
RECOMMENDATION: Make `/pair` degrade with zero script: add a second paragraph and link to `site/public/pair.html` — "No AgentPort extension? Open the AgentPort Wallet and paste the code your terminal printed" pointing at the wallet origin — so the page is useful before any JS could run and the invariant that it cannot sign is untouched. In parallel change the daemon's pairing print (`packages/daemon/src/cli.ts`) to name both routes rather than one URL. `wallet/src/app.ts` already consumes `#code=`, so no wallet work is needed. Then add this to the stranger-walk obligation as an artifact check: fetch the deployed `/pair` and assert it names a route reachable without an extension.

## [P0/S] MOVE 2 — The live landing page's hero snippet throws before it reaches the network
The deployed landing page — the most-copied integration surface on the internet for this project — shows `alwaysAsk: ['inkwell.document.replaceSelection']` while the `tools` array in the same snippet declares only `inkwell.document.read`. `packages/client/src/wallet.ts#buildGrant` rejects that combination and `explainGrantViolation` renders it as "every name in alwaysAsk must also be the name of a tool you passed", so the snippet fails at `connect()` for anyone who copies it verbatim. Separately the snippet's `<script>` tag carries neither `data-relay` nor `data-wallet`, and `site/src/connect.ts#relayUrl` then falls back to `ws(s)://<embedding-host>/relay` — correct on our own origin, and a guaranteed "could not reach the relay" for any third-party adopter. README.md and `docs/APP-BUILDER.md` both get this right; the landing page does not, which reproduces the "a landing page and a README giving different instructions for the same step" defect the north star already recorded once.
EVIDENCE: `site/public/index.html` hero `<pre>` (deployed copy verified identical); `packages/client/src/wallet.ts#buildGrant`, `#explainGrantViolation`; `site/src/connect.ts#relayUrl`, `#scriptAttribute`; contrast `README.md` and `docs/APP-BUILDER.md` §1
RECOMMENDATION: Replace the landing hero snippet in `site/public/index.html` with the exact README snippet including `data-relay` and `data-wallet`, and make it executable rather than decorative: add a harness (alongside `scripts/ui-smoke.ts`) that extracts the snippet from `site/public/index.html` and `README.md`, serves it from a foreign origin, loads the built `site/public/connect.js` by classic `<script src>`, and asserts `connect()` gets past `buildGrant` and reaches a relay dial. That is an artifact property, not an encoding of what we believe a visitor does — the same shape as the existing 'connect.js parses under the Script goal' guard that caught the previous instance.

## [P1/M] MOVE 3 — The default runtime has an undeclared prerequisite and fails opaquely at attach time
`packages/cli/src/main.ts#defaults` sets `AGENTPORT_RUNTIME ??= 'claude-code'`, which `packages/daemon/src/cli.ts` registers as an `AcpRuntime` spawning `npx -y @agentclientprotocol/claude-agent-acp` (`packages/daemon/src/acp-command.ts` DEFAULT_COMMAND/DEFAULT_ARGS). That requires Claude Code to be installed and authenticated on the machine, and nothing states this: the string "claude login" appears in no document, and `packages/cli/README.md`'s configuration table lists five variables without mentioning the dependency. `AcpRuntime` never reads `init.authMethods` and never calls ACP `authenticate` (`packages/daemon/src/runtimes/acp.ts` — the only `initialize` request sets `clientCapabilities` and moves straight to `session.new`), so an unauthenticated machine pairs successfully, prints a happy pairing message, and then fails at the first `Connect agent` inside `AgentDaemon`'s `runtime.openSession` catch — a failure that arrives in the browser, minutes later, far from its cause. `AGENTPORT_AGENT_CWD`, the variable that decides what the agent can actually see on the user's disk, appears in zero markdown files in the repository.
EVIDENCE: `packages/cli/src/main.ts#defaults`; `packages/daemon/src/acp-command.ts#resolveAcpCommand`; `packages/daemon/src/runtimes/acp.ts` (no `authenticate`, no `authMethods` read); `packages/daemon/src/daemon.ts` runtime.openSession failure path; `packages/cli/README.md` configuration table; `AGENTPORT_AGENT_CWD` present only in `packages/daemon/src/cli.ts`, `connect-cli.ts`, `runtimes/acp.ts`, `deploy/agentport.service`
RECOMMENDATION: Add `agentport doctor` to `packages/cli/src/main.ts` that spawns the resolved ACP pair, completes `initialize`, reports `agentCapabilities.loadSession` and any `authMethods` the agent advertises, and exits non-zero with the remediation command — and run it implicitly on first start before printing a pairing code, so the failure lands in the terminal that can fix it. Handle the ACP `authenticate` method in `packages/daemon/src/runtimes/acp.ts` rather than letting `session.new` fail. Document the Claude Code prerequisite and `AGENTPORT_AGENT_CWD` in `packages/cli/README.md` and `README.md`; `AGENTPORT_AGENT_CWD` is the highest-consequence undocumented variable in the project.

## [P1/L] MOVE 4 — Pick the wedge explicitly: the generic page harness, not the script tag
There are exactly two integrations in existence, both authored here and both toys: `site/src/inkwell.ts` (7 tools) and `site/src/tasker.ts` (5 tools); `examples/` contains only inkwell. The script-tag story asks a site to add a feature that today serves approximately zero of its visitors, which is an unwinnable cold start — and `docs/reviews/prior-art-synthesis.md` cluster 6 already establishes the correct read: Payment Handler failed as a platform and Secure Payment Confirmation survived because one flow was measurably better for the site, so `navigator.agent` adoption comes from a flow, not from elegance. Meanwhile the one capability no site and no browser vendor can supply is already built: `packages/extension/src/pagetools.ts` lends `page.info/readText/readSelection/listElements/scroll` ungated and `page.fill/page.click` gated, on sites that declared nothing, through the same grant, consent and sealing path — and it is the *user's own* agent, with their files and MCP servers, which a browser-vendor assistant structurally cannot be. That is the wedge. The site-side proposition ("an assistant with no inference bill and no SDK") only becomes real once a population of users already carries an agent, and the harness is what creates that population without any site's cooperation.
EVIDENCE: `site/src/inkwell.ts`, `site/src/tasker.ts`, `examples/inkwell` (only integrations); `packages/extension/src/pagetools.ts` tool set; `docs/reviews/prior-art-synthesis.md` cluster 6 Payment Handler postmortem; `docs/NORTH-STAR.md` "The widest form of the claim"; ADR-021 in `docs/ADR.md`
RECOMMENDATION: Reorder the public story around the harness: make the README's and landing page's primary call-to-action "install the extension, attach your agent to any site" and demote the script tag to the app-builder path it already documents well. Then close ADR-021's two named blockers, which are the harness's product-quality gates and not security work: session survives same-origin navigation (`packages/extension/src/sw.ts`, where only `from === 'page'` surfaces get orphan-and-reclaim) and `page.navigate` as a real tool (`packages/extension/src/pagetools.ts`). Do NOT ship remembered consent alongside them — `docs/reviews/web-harness-consent.md` rejected per-action-class memory and ADR-023's authority domain is the prerequisite; the corrected model remembers attaching and reading only.

## [P1/L] MOVE 5 — Extension distribution is engineering, not a release decision, and it gates three signals
AGENTS.md states "That is a release decision, not engineering." Checked against the manifest and the extension's own README, that is false. `packages/extension/static/manifest.json` requests `host_permissions: ["http://*/*", "https://*/*"]` plus an `all_frames`, `document_start` content script on every URL — the strongest permission set in the Chrome Web Store's review taxonomy, which forces a written single-purpose statement, per-permission justification, extended review latency, and a hosted privacy policy that does not exist in this repository. The broad host permission is architecturally load-bearing (the WebMCP shim in `src/inpage.ts` must be installed before page scripts run, so `activeTab` cannot substitute), so it must be justified rather than reduced — which is a documentation-and-review project, not a checkbox. Three of the extension's own "What is stubbed" entries are also materially different at store scale than at load-unpacked scale: `ensureUserKey` in `src/storage.ts` writes a raw hex root key with no passkey wrapping; there is no revocation UI in the popup, so a store user has no way to see or cut off what holds their agent without the CLI; and store assets beyond `static/icon128.png` (screenshots, promo tile) do not exist. The extension README's own setup step is already stale against the code — it says "Set the relay if it is not ws://127.0.0.1:8787" while `src/storage.ts#DEFAULT_RELAY_URL` is the hosted `wss://` relay.
EVIDENCE: `packages/extension/static/manifest.json` (`host_permissions`, `content_scripts` matches/all_frames/run_at); `packages/extension/README.md` "What is stubbed" (`ensureUserKey`, "No revocation UI"); `packages/extension/src/storage.ts#DEFAULT_RELAY_URL` vs README step 4; `packages/extension/static/` contains only `icon128.png` and `consent.html`; ADR-022 revocation is CLI-only (`docs/ADR-022-revocation.md`, ADR-014 item 3)
RECOMMENDATION: Treat this as a tracked engineering item with four deliverables: (1) a privacy-policy page served by the site Worker (`site/public/`, `site/src/worker.ts`) plus the single-purpose and permission-justification text, written against `docs/ADR-018` and the extension README's trust-boundary section which already contains the argument; (2) passkey wrapping in `packages/extension/src/storage.ts#ensureUserKey` — the README says this touches one file, and shipping a plaintext root key to strangers is the one item here I would gate the listing on; (3) a revocation surface in `packages/extension/src/popup.ts` calling the daemon revoke path ADR-022 already built, so an installed user can see and cut off what holds their agent; (4) listing assets. Correct the stale relay instruction in `packages/extension/README.md` in the same pass. This is the gate on signals 2, 5 and 6, so it is the highest-leverage L-sized item in the list.

## [P1/S] The site is still told which runtime the user runs — the one item on the "learns nothing" list that is false in shipped code
`docs/NORTH-STAR.md` puts "which runtime" first on the list of things the site never learns, and calls that list "the whole product". `packages/daemon/src/daemon.ts` sends `runtime: this.#options.identity.runtime` on `session.opened` and `session.resumed` unconditionally, including in the delegated hosted-wallet tier where the sibling field is deliberately redacted to `Personal agent` via `responseAgentName`/`resumedAgentName`. `docs/APP-BUILDER.md` documents the leak honestly ("Exposing the runtime to the page conflicts with AgentPort's privacy goal and is a known protocol gap") and asks app authors not to make it harder to remove — which is a request, not a control. Every other requirement on that list is enforced with an adversarial check; this one is enforced by asking integrators nicely.
EVIDENCE: `docs/NORTH-STAR.md` "What 'the site learns nothing' means"; `packages/daemon/src/daemon.ts` `responseAgentName` and the adjacent `runtime:` fields on the opened/resumed responses and the EPK proof binding; `docs/APP-BUILDER.md` §3 runtime paragraph; `packages/protocol/src/messages.ts` session.opened schema
RECOMMENDATION: Redact `runtime` for delegated sessions exactly as `agentName` already is, and drop it from the page-facing handle entirely at the next wire cutover. Flagging the gate explicitly: the field is inside the `answerProofBinding` EPK transcript, so changing it is a lockstep protocol change — `PROTOCOL_VERSION` in `packages/protocol/src/messages.ts` must bump to `agentport/7` and relay, wallet, extension and CLI must ship together per `docs/RELEASING.md`. Batch it with the next wire change rather than spending a cutover on it alone, and add the adversarial e2e assertion (a delegated page cannot learn the runtime string) in the same commit.

## [P2/M] Adoption-signal blocker map: the single biggest blocker for each of the six
(1) A site adopts without talking to us — blocker: the live landing snippet does not run (MOVE 2); the app-builder guide is genuinely good, but the page a stranger actually copies from is the broken one. (2) A WebMCP-only site works for free — blocker: extension distribution, because the drop-in path requires the site to load `connect.js` first (ADR-006 point 1 harvests only registrations made after our script is present), and a pure-WebMCP site has no reason to load it at all; the actually-free path is the extension's `src/inpage.ts` shim, which needs a store listing. (3) Third-party relay — blocker: not the relay, which is verified working and now documented; it is that no wallet can record which relay an agent lives on, so a user cannot hold one agent on their own relay and another on the hosted one. (4) Third-party runtime — blocker: it works, but `packages/daemon/src/identity.ts#loadIdentity` freezes `runtime` at file creation, so someone who swaps to goose keeps a cert and picker entry stamped `claude-code`; the label the user checks to confirm the swap worked is the thing that lies. (5) Two unrelated sites in one afternoon — blocker: there are no unrelated sites; both surfaces are ours (MOVE 4). The mechanics already work — the hosted wallet remembers certs on its own origin and the second connect needs no re-pairing. (6) Someone argues it belongs in the browser — blocker: no demonstrated demand, which per `docs/reviews/prior-art-synthesis.md` is precisely the Blink evidence checklist item the extension provider is supposed to supply; it depends on 5, which depends on 2.
EVIDENCE: `site/public/index.html`; `packages/client/src/webmcp.ts#WEBMCP_NOT_IMPLEMENTED` and ADR-006 points 1–8; `docs/worklists/hosted-wallet-report.md` risk 6 ("Cert storage does not yet carry relay metadata") and ADR-016 pending CODE@relay URIs; `packages/daemon/src/identity.ts#loadIdentity` (defaults applied only on ENOENT) with `packages/daemon/src/cli.ts` `runtimeName`; `docs/reviews/prior-art-synthesis.md` cluster 6
RECOMMENDATION: Two cheap fixes fall out directly and are worth doing before the L-sized moves. Refresh `runtime`, `name` and `location` from the environment on every `loadIdentity` load in `packages/daemon/src/identity.ts` (the device key is what must be stable, not the labels), and re-sign or re-announce accordingly — otherwise signal 4 is walkable and still reports the wrong answer. Carry a relay URL on the stored cert record in `wallet/src/storage.ts` and `packages/extension/src/storage.ts`, which is ADR-016 rung A's `CODE@relay` work reduced to its smallest useful form and is what makes signal 3 true for a user rather than only for an operator.

## [P2/M] "Your memory" is delivered by working directory and config, not by conversation — the claim should narrow or the capability should grow
The pitch that separates this from a site chatbot is that the attached agent already knows you. `packages/daemon/src/runtimes/acp.ts` calls ACP `session.new` for every attachment with `cwd` and the session's `mcpServers`, and never calls `loadSession` for any pre-existing user conversation — `loadSession` is used only to replay AgentPort's own resumed session (`replayHistory`). So the borrowed agent arrives with the user's files, their CLAUDE.md, their MCP servers and their prompts — real and valuable — but with zero conversational memory of anything the user has done. `docs/NORTH-STAR.md` and both READMEs say "with your memory", which a first user will read as the stronger claim and find false on first prompt. The same code path also creates one ACP child process per attachment (`createRuntime()` per session in `AgentDaemon`), so "two sites in one afternoon" is two concurrent agent processes with no shared context between them.
EVIDENCE: `packages/daemon/src/runtimes/acp.ts` (`session.new` per attachment; `#supportsLoad` used only by `replayHistory`); `packages/daemon/src/daemon.ts` `createRuntime()` invoked per session; `docs/NORTH-STAR.md` "The claim"; `README.md` "with their memory, prompts, and MCP servers"
RECOMMENDATION: Choose one. Either narrow the wording in `docs/NORTH-STAR.md`, `README.md` and `packages/cli/README.md` to what is true — your files, your prompts, your MCP servers, your subscription — which costs nothing and removes a first-prompt disappointment; or build the capability, an opt-in "continue from my last session" that resolves an existing ACP session id through `loadSession` at attach time, decided at the daemon and never by the page. The second is a genuine differentiator over any site chatbot and is exactly the kind of capability work the owner's directive prefers, but note the boundary: a resumed conversation carries prior context into a session whose tools a site now supplies, so it must not bypass `AgentDaemon#authorityError` or the grant, and the prompt-injection note in AGENTS.md applies with more force.

## [P3/S] Deployed state matches main, and that fact should be made cheap to re-check
AGENTS.md warns that landed is not shipped and asks the reader to compare `PROTOCOL_VERSION` at the last release commit against main's. Checked: the hosted `/connect.js` is byte-identical to `site/public/connect.js` (sha1 7d0cfd743e60e19ea5045f7868d72d378bcffbd3), both carry `agentport/6`, and only `f7c8ee6` (a CI-only change) sits after tag `v0.1.7`. So the warning is currently satisfied — but establishing that took a manual fetch, a shasum and a git log, which is the same shape of friction that lets drift go unnoticed between releases. The release workflow already proves the npm tarball against the deployed relay before publishing; nothing proves the *browser bundle* a stranger downloads matches the commit.
EVIDENCE: hosted `https://agentport.gogakoreli.workers.dev/connect.js` sha1 equals `site/public/connect.js`; `packages/protocol/src/messages.ts#PROTOCOL_VERSION` = `agentport/6`; `git log v0.1.7..main` = one CI commit; `docs/RELEASING.md` deploy-stage smoke covers the npm tarball only
RECOMMENDATION: Add a `scripts/deployed-check.ts` that fetches `/connect.js` and `/pair` from the configured hosted origin and asserts the bundle hash matches the local build and that the version/commit stamp `scripts/deploy.ts` bakes in matches `git rev-parse HEAD`. Wire it into the release workflow beside the existing tarball smoke in `.github/workflows/auto-tag.yml`. This is the artifact-level half of the stranger walk, in the same spirit as the existing Script-goal parse guard, and it makes the "landed is not shipped" question answerable by one command instead of three.
