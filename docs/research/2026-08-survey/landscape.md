# SUMMARY
Between May and August 2026 the landscape moved decisively on the half of AgentPort's thesis it does NOT own — the supply of site-declared tools — and barely at all on the half it does own: who the agent is and how a user lends it to a site.

Verified: WebMCP is a W3C Web Machine Learning CG **Draft Community Group Report dated 2026-08-19** (not standards-track), the API is now `document.modelContext.registerTool(tool, {exposedTo, signal})` with `getTools()`/`executeTool()`/`toolchange`, plus a declarative HTML-form variant; it is in a Chrome origin trial from Chrome 149 (docs last updated 2026-08-07). Supply then arrived in one week: **Cloudflare shipped a WebMCP developer preview on 2026-08-06** that injects a bridge script at the edge via HTMLRewriter for any site on its network, and Shopify is reported (secondary) to have switched WebMCP on across Liquid storefronts on 2026-08-05. So "a site that declares tools" stopped being rare — without any site adopting AgentPort.

Meanwhile MCP had its largest breaking revision ever (**2026-07-28**): protocol-level sessions and the `initialize` handshake removed, `server/discover` added, all results carry `resultType`, server-initiated elicitation/sampling/roots replaced by the **Multi Round-Trip Requests** pattern (`InputRequiredResult` + `requestState`), and Sampling/Roots/Logging formally deprecated. AgentPort's `McpBridge` targets the old shape. ACP shipped **1.0.0 on 2026-06-24 through 1.6.0 on 2026-07-21**, made `mcpServers` optional, unified `session/load` and `session/resume` under `sessionCapabilities`, and has an **Active RFD (2026-07-02) for ACP over Streamable HTTP and WebSocket** — the single most consequential item here, because it is a standards path to "attach a remote agent" that currently defers origin validation and security to a later phase.

On the differentiator itself the claim still holds and is now sharper: no browser or OS vendor lets a user supply their own remote agent. Gemini in Chrome, Perplexity Comet, Edge, and Dia are all vendor-agent-only; ChatGPT Atlas was retired (reported 2026-08-09) into the ChatGPT desktop app and a Chrome extension. The closest thing to AgentPort is **Claude in Chrome, GA in Claude Code v2.1.198 (week of 2026-06-29)**, where "Claude Code drives your browser" — but the bridge is a *local native-messaging host*, a single vendor's agent, a direct Anthropic plan, and the site is not a party: no lent toolset, no grant, no consent surface, no remote daemon. That gap is the product. The clock on it is that WebMCP's default exposure is "same-origin documents and built-in browser agents", which structurally privileges the browser vendor's agent over anyone else's.

## WebMCP spec (W3C Web Machine Learning CG)
STATUS: VERIFIED (fetched spec + explainer + Chrome docs): Draft Community Group Report dated 2026-08-19, explicitly "not a W3C Standard nor on the W3C Standards Track". Editors from Google and Microsoft. API is `document.modelContext.registerTool({name, description, inputSchema, execute}, {exposedTo, signal})`, plus `getTools()` (accepts `fromOrigins`), `executeTool()` (accepts `signal`; returns null when a navigation is triggered) and a `toolchange` event. A declarative counterpart synthesizes tools from `<form>` elements (annotations like `toolname`/`tooldescription`; Angular has experimental support). Annotation hints include `readOnlyHint` (may skip explicit confirmation) and `untrustedContentHint` (external data needing scrutiny). Permissions Policy `tools` defaults to `self`; a cross-origin iframe needs `allow="tools"`. Documents that opt out of origin isolation (`Origin-Agent-Cluster: ?0` / `document.domain`) cannot use the API. INFERRED/SECONDARY: the `navigator.modelContext` → `document.modelContext` move landed around the 2026-07-21 draft with Chrome 150 deprecating the old location, so `document.modelContext ?? navigator.modelContext` is the current compatibility idiom.
RELEVANCE: This is AgentPort's declared-tool input side and the format `SiteTool` is meant to converge on. Three things changed under `packages/client/src/webmcp.ts` since it was written: the registration options object (`exposedTo`), the declarative form-synthesized tools, and `toolchange` (a live grant should track it rather than harvesting once at attachment). Critically, the explainer names three consumer classes — built-in browser agents, author-provided agents in iframes via `allow="tools"`, and extension-based agents — and says default exposure is same-origin documents plus **built-in browser agents**. A user-supplied REMOTE agent is not a named class anywhere in the spec.

## MCP specification 2026-07-28
STATUS: VERIFIED (fetched changelog + RC blog): RC locked 2026-05-21, published 2026-07-28. Major: (1) protocol-level sessions and `Mcp-Session-Id` removed; list endpoints no longer vary per connection. (2) MCP is stateless — `initialize`/`notifications/initialized` removed; every request carries `io.modelcontextprotocol/protocolVersion` and client capabilities in `_meta`; mismatches return `UnsupportedProtocolVersionError`. (3) New mandatory `server/discover` RPC advertising supported versions, capabilities, identity. (4) `subscriptions/listen` replaces the HTTP GET endpoint and `resources/subscribe`. (5) `ping`, `logging/setLevel`, `notifications/roots/list_changed` removed. (6) Tasks moved to an official extension with `tasks/get`/`tasks/update`/`tasks/cancel`. (7) **MRTR**: servers return `InputRequiredResult` (`resultType: "input_required"`) with `inputRequests`; clients retry the original request with `inputResponses` — this replaces server-initiated `elicitation/create`, `sampling/createMessage`, `roots/list`. (8) All results carry a required `resultType`. (9) SSE resumability and `Last-Event-ID` removed. Minor: required `Mcp-Method`/`Mcp-Name` headers, required `ttlMs`/`cacheScope` on list/read results, deterministic tool ordering, JSON Schema 2020-12 loosening, `iss` validation per RFC 9207, Client ID Metadata Documents replacing DCR. Deprecated: **Roots, Sampling and Logging** (12-month window), HTTP+SSE transport, `includeContext` values.
RELEVANCE: `McpBridge` (the loopback, token-scoped MCP server that carries the site's grant into the ACP agent) is written against the old shape and will need: no handshake, `server/discover`, `resultType` on every result, `ttlMs`/`cacheScope` on `tools/list`, and the MRTR pattern. MRTR is genuinely GOOD news for AgentPort — an approval/question round-trip modelled as "return input_required, client retries with the answer" matches the wallet round-trip better than a server-initiated request did, and `requestState` gives the bridge a place to carry the attachment/authority binding across the retry. Sampling's deprecation also permanently closes the worst leak shape (a lent tool asking the user's model to generate), which AgentPort never exposed anyway.

## ACP (Agent Client Protocol) — releases and shape
STATUS: VERIFIED (fetched CHANGELOG + docs): 1.0.0 on 2026-06-24, then 1.1.0 (2026-06-24), 1.2.0 (2026-06-29, request cancellation stabilized, v2 auth grouped under `auth/*`, **`mcpServers` made optional in `session/new`**), 1.3.0 (2026-07-06, boolean session config stabilized, **`session/load` and `session/resume` unified**, permission-request flexibility), 1.4.0 (2026-07-06, descriptions on elicitation enum options), 1.5.0 (2026-07-20, v2 semantic string types, v2 terminal output surface, auth methods gated on `authMethods` capability), 1.6.0 (2026-07-21, tool-call name and cancelled variants in unstable-v2). Current docs still describe `/protocol/v1/*`; `session/new` takes `mcpServers: McpServer[]`, `session/load` requires the `loadSession` capability and replays the whole conversation via notifications, and there is now a `sessionCapabilities` object covering `close`, `delete`, `list`, `resume`. The session-resume RFD (capability shape settled to `sessionCapabilities.resume` on 2026-04-14) adds `session/resume` that continues WITHOUT replaying history, explicitly so adapters can convert `session/load` into `session/resume` for resume-only agents. An `unstable-v2` track is clearly in flight.
RELEVANCE: Two direct hits. First, AgentPort's daemon injects the grant as `mcpServers[]` in `session/new` — now optional, and the v2 track is reworking auth, config and terminal surfaces, so `AcpRuntime` has a migration ahead. Second, AgentPort's own resume semantics (`replayHistory()` falling back to the daemon's in-memory transcript when the runtime returns null) now have an upstream analogue: `session/resume` for continuing silently vs `session/load` for replay is exactly the distinction the panel's `history.request` path makes by hand.

## ACP remote transport RFD (Streamable HTTP + WebSocket)
STATUS: VERIFIED (fetched RFD): status **Active**, dated 2026-07-02, positioned as an additive feature for ACP v1. A single `/acp` endpoint: POST for client→server (`initialize` returns 200 with JSON, others 202), GET without upgrade opens SSE streams (one connection-scoped plus one per session), GET with `Upgrade: websocket` for full-duplex, DELETE to terminate. "ACP authentication is orthogonal and layered on top via HTTP headers, query parameters, or WebSocket subprotocols"; `Acp-Connection-Id`/`Acp-Session-Id` are explicitly NOT auth tokens. Sessions persist server-side independent of any connection and resume via `session/load`. Clients MUST accept/store/return cookies for session affinity; Streamable HTTP MUST use HTTP/2. Browsers/web clients are NOT explicitly addressed. Origin validation, `Acp-Protocol-Version` and SSE resumability are deferred to a "Phase 4" hardening pass alongside a planned security audit.
RELEVANCE: This is the closest thing to an existential item and simultaneously the biggest opening. It standardizes "talk to a remote agent over a WebSocket" — the transport half of AgentPort — while explicitly punting the parts AgentPort has already built and adversarially tested: origin identity, per-session capability grants, consent at the key, end-to-end sealing so the transport operator cannot read content, and ownership certs. The cookie-based session affinity requirement is also actively hostile to a browser-origin client. AgentPort has running answers to a document that says these are future work.

## Web Bot Auth (IETF)
STATUS: VERIFIED-ish (IETF datatracker + Cloudflare blog + secondary): built on RFC 9421 HTTP Message Signatures, an Ed25519 key per agent, a `Signature-Agent` header and a JWKS directory; drafts include `draft-meunier-web-bot-auth-architecture` and `draft-meunier-webbotauth-registry` (Signature Agent Card). An IETF WebBotAuth **working group was chartered in 2026** after a BoF at IETF 123, co-chaired by David Schinazi and Rifaat Shekh-Yusef, with milestones for standards-track auth techniques and a BCP on key management. Cloudflare has folded message signatures into its Verified Bots program. SECONDARY: as of 2026-08-12 the WG reportedly has no adopted documents yet; backers include Cloudflare, Amazon, Akamai and OpenAI.
RELEVANCE: The web is standardizing "this request comes from an agent, and here is its Ed25519 key" at the HTTP layer — conceptually the same primitive as AgentPort's `AgentCert` (a device key + a signature binding it to a principal), in a different layer and a different venue. If AgentPort's daemon or extension ever fetches on the user's behalf, this is the format that decides whether it is treated as a bot or a user. It is also the most credible external home for publishing an agent's public key, versus AgentPort's own directory.

## AP2 / Verifiable Intent → FIDO Alliance
STATUS: SECONDARY-to-good: AP2 was announced 2025-09-16 by Google with 60+ partners; every purchase is three signed W3C Verifiable Credentials — Intent Mandate, Cart Mandate, Payment Mandate — signed by the user's wallet or the agent's key. Public deployments as of April 2026 include PayPal + Google Cloud Conversational Commerce, Mastercard Agent Pay in PayPal, and the A2A x402 crypto extension. **On 2026-05-26 the FIDO Alliance announced that Google's AP2 and Mastercard's Verifiable Intent had been contributed to it.**
RELEVANCE: This is the delegation model AgentPort already implements (`SessionDelegation`: user key signs a bounded, origin-scoped, expiring authority for an agent to act) being standardized as signed mandates, now under the same body that runs passkeys. AgentPort's cert-plus-delegation is a bespoke encoding of a shape the industry is converging on — an argument for expressing it as a VC/mandate profile rather than defending a private format.

## WebAuthn Level 3 and the `sign` extension
STATUS: VERIFIED-ish: W3C published a **Candidate Recommendation Snapshot of WebAuthn Level 3 on 2026-01-13**, remaining CR at least until 2026-06-23. The `sign` extension (w3c/webauthn PR #2078, with a Yubico draft repo for sign/KEM extensions) lets a relying party sign **arbitrary data** with a key held by the authenticator; the signing keypair is deliberately distinct from the parent WebAuthn credential key so arbitrary input cannot bypass domain binding. The PRF extension is the established route for deriving encryption keys from a passkey.
RELEVANCE: This is the concrete path off raw Ed25519 user-key custody that the north star anticipates ("swapping raw Ed25519 for a bunker or a passkey touches one file"). Note the shape mismatch worth designing around: AgentPort signs Ed25519 over canonical JSON, whereas `sign` gives ES256/EdDSA over arbitrary input with its own key hierarchy, and PRF gives a derived secret rather than a signature — so the wallet abstraction has to be over "produce a signature for this canonical body", not over "here is an Ed25519 secret".

## NIP-46 / NIP-07 remote signing
STATUS: VERIFIED-ish (no material 2026 movement found): NIP-46 remains the stable pattern — a bunker holds the key and signs over relays; NIP-07 remains the in-page `window.nostr` surface. Live bridges exist (Bunker46 extension providing `window.nostr` while forwarding every request to a remote NIP-46 signer; a "Remote NIP-07" Chrome extension using QR handoff; nostr-signer-connector supporting both signer-initiated and client-initiated discovery). No spec-level change surfaced.
RELEVANCE: Still the best analogy for what AgentPort is doing, and still not a moving target — meaning the `window.nostr` framing in the README ages well. The bridge extensions are worth reading as prior art for the exact tier ladder AgentPort implements (in-page provider → extension → remote signer), including how they handle a resume/handoff without ever exposing the root key.

## W3C agent-adjacent community groups
STATUS: VERIFIED (W3C group pages + search): the **AI Agent Protocol CG** (`public-agentprotocol`, first meeting 2025-06-18, bi-weekly, mission is discovery, identity and collaboration protocols for agents on the web); **Autonomous Agents on the Web CG**; and two 2026 arrivals — **Agent Identity Registry Protocol CG** (proposed 2026-04-22) and **Agent Trust Protocol (ATP) CG** (proposed 2026-06-04). Nobody is working on the specific inversion AgentPort makes — the SITE lending capability to a USER-CHOSEN agent — but the identity and delegation substrate is being poured now, and it will be much cheaper to align with it than to retrofit later.

# OPPORTUNITIES
- **Cut the MCP bridge over to 2026-07-28 and use MRTR for approvals.** `McpBridge` targets the pre-2026 shape; the new spec removes `initialize`, requires `server/discover`, requires `resultType` on every result, requires `ttlMs`/`cacheScope` on `tools/list`, and replaces server-initiated `elicitation/create` with `InputRequiredResult` + `requestState` retries. This is not just maintenance: MRTR is a *better* fit for AgentPort than what it replaces, because a lent tool needing user approval or an answer can now return `input_required`, and the daemon can carry the attachment authority in `requestState` and re-judge the grant on the retry — which is exactly the boundary `AgentDaemon#authorityError` already enforces at four points. The stateless-server model also matches a per-attachment bridge that mints and withdraws with the session. Sampling and Roots being deprecated permanently closes two shapes a lent toolset must never express.
- **Own the WebMCP harvest properly, and treat the new metadata as adversarial input.** Update `packages/client/src/webmcp.ts` for `document.modelContext` with the `navigator` fallback, the `{exposedTo, signal}` registration options, `getTools({fromOrigins})` for cross-origin, and the `toolchange` event so a grant tracks a page that adds tools mid-session instead of freezing at attachment. Then take a position, in code and in `WEBMCP_NOT_IMPLEMENTED`, on the annotation hints: `readOnlyHint` exists to let an agent skip confirmation and is authored by the page, so it must never lower AgentPort's gate; `untrustedContentHint` may only ever RAISE scrutiny. Declarative form-synthesized tools carry page-authored `toolname`/`tooldescription` strings straight to a consent surface, which is precisely the `display()` versus `str` distinction already fought for.
- **Be the first consumer where the supply just landed.** As of the first week of August 2026 every Cloudflare-fronted site can flip on WebMCP and (reported) every Shopify Liquid storefront already has it, while by July 2026 no mainstream agent consumed WebMCP at all. That is a supply glut with no demand — the exact inverse of the adoption problem requirement 6 worries about, and AgentPort is a demand-side product. Concretely: a stranger-walk on a real Shopify storefront and a Cloudflare-preview site with nothing but the extension installed, and a demo where a user's own remote agent buys something on a store that has never heard of AgentPort. That single artifact answers "why would a site adopt this" with "it already did".
- **Take the seat that the ACP remote-transport RFD leaves empty.** The RFD is Active, dated 2026-07-02, and explicitly defers origin validation, `Acp-Protocol-Version`, and the security audit to a later phase, while not addressing browsers at all and mandating cookie-based session affinity that a browser-origin client cannot supply cleanly. AgentPort has running, adversarially tested answers to each: relay-stamped identity, an ownership cert checked at both edges, per-attachment X25519 sealing so the transport operator sees ciphertext, protocol-version binding inside the EPK proof transcript (the exact split-negotiation attack the RFD's missing `Acp-Protocol-Version` invites), and a resume token that the routing party cannot use. Contributing that experience — as review, as a browser-profile proposal, or as a reference implementation — is the cheapest available path from "a project" to "a primitive".
- **Align the ACP runtime with the v2 track and with `session/resume`.** ACP 1.2.0 made `mcpServers` optional, 1.3.0 unified `session/load` and `session/resume`, and the unstable-v2 track is reworking auth (`auth/*`), semantic string types, terminal output and permission requests. AgentPort already distinguishes "resume the session silently" from "replay history for a reloaded page" by hand in the daemon; that is now an upstream capability distinction (`sessionCapabilities.resume` vs `loadSession`). Mapping AgentPort's `history.request` onto whichever the runtime actually advertises — instead of assuming `loadSession: true` because `claude-agent-acp` happens to advertise it — makes the provenance table true for the other 59 agents too.
- **Move user-key custody onto the standard track rather than defending a bespoke one.** WebAuthn L3 has been a Candidate Recommendation since 2026-01-13, the `sign` extension for arbitrary-payload signing is progressing in w3c/webauthn#2078, and AP2's mandate model — user's wallet signs a scoped, verifiable authorization for an agent to act — was contributed to the FIDO Alliance on 2026-05-26. AgentPort's `AgentCert` and `SessionDelegation` are the same idea in a private encoding. Two cheap moves: make the wallet interface "sign this canonical body" rather than "hold this Ed25519 secret" (so passkey `sign`, a NIP-46 bunker, and the extension are all one implementation), and publish a mapping from `AgentCert`/`SessionDelegation` to a Verifiable Credential profile so the ownership model is legible to people already reading mandates.
- **Reuse Web Bot Auth's key-publication shape for the agent's identity on the open web.** RFC 9421 signatures, an Ed25519 key per agent, a `Signature-Agent` header and a JWKS/Signature-Agent-Card directory are being standardized in a chartered IETF WG with Cloudflare, Amazon, Akamai and OpenAI behind them, and Cloudflare already verifies them in production. AgentPort's daemon already has an Ed25519 device key that never leaves the VPS. Publishing that key in the format the edge already checks is the difference between an agent that gets served and one that gets challenged — and it costs a directory endpoint, not a design change.
- **File the missing consumer class in the WebMCP explainer.** The explainer names built-in browser agents, author-provided iframe agents, and extension-based agents; a user-supplied REMOTE agent reached through an extension is unnamed, and default exposure goes to the browser's own agent. Getting that fourth class written down — with a concrete argument that a site benefits from lending tools to an agent the user already trusts, and that consent belongs where the user's key is — is a small standards contribution with an outsized effect on whether `exposedTo` defaults ever lock AgentPort out. It is also the one WebMCP signal in the north star that has already been walked once, so the muscle exists.
- **Ship the Chrome Web Store listing.** The nearest occupant of this niche, WebMCP Bridge, has 178 users, v0.1.0, and last shipped 2026-04-05. AgentPort's own notes already say the boundary is built and only distribution is left. In a month where two of the largest hosting platforms turned on tool supply by default, an unlisted load-unpacked build is the binding constraint on every other item on this list.

# THREATS
- **WebMCP's default exposure privileges the browser's own agent.** The explainer states tools are exposed by default to same-origin documents and **built-in browser agents**; everyone else needs the site to name them in `exposedTo` or an iframe to carry `allow="tools"`, and the `tools` Permissions Policy defaults to `self`. If that default survives to shipping, Gemini in Chrome sees a site's tools for free while a user-supplied agent sees whatever a site remembered to authorize — and AgentPort's harvest degrades most on exactly the sites that adopted WebMCP. Defence: verify empirically what an extension actually receives on a Cloudflare/Shopify page today, and argue the fourth consumer class into the spec before the default hardens. If the default does hold, the extension's generic page harness — which the north star already flags as incomplete, with `page.navigate` proposed in ADR-021 and unbuilt — becomes the primary path again, and its failure modes become the product's.
- **Claude in Chrome is the widest-form claim, shipped.** GA since Claude Code v2.1.198 (week of 2026-06-29): the agent you already use, acting on the page in front of you, with your login state, on any site, declared or not. It is the single sentence AgentPort's north star uses to distinguish itself from a browser-vendor assistant. What AgentPort still has that it does not: runtime independence (60+ ACP agents vs one vendor), remoteness (their bridge is a local native-messaging host binding agent and browser to one machine, and refuses API-key sessions outright), and a site-facing protocol (their site is not a party — it declares nothing, lends nothing, gets no session, and cannot scope what the agent may do on it). Defence is to say exactly that, and to make the remote case undeniable: an agent on a VPS driving a laptop browser, and a site scoping its own tools, are both things native messaging structurally cannot do.
- **A breaking MCP cutover can silently disarm the lent toolset.** The 2026-07-28 revision removes the handshake, adds a mandatory `server/discover`, requires `resultType` on every result, and returns `UnsupportedProtocolVersionError` on mismatch. The moment the ACP agent's MCP client moves — and `claude-agent-acp@0.70.0` already tracks fast-moving SDKs — the site's grant either stops loading or, worse, loads with a subset of behaviour. This is the same lockstep-cutover hazard AgentPort already understands for its own wire, applied to a dependency it does not control. Defence: pin and assert. A check that the bridge answers `server/discover` with the version it claims, and that fails when the runtime's MCP client speaks a version the bridge does not — rather than a silently empty tool list, which is the failure mode this repo's own tenets call the invisible diminishment.
- **ACP over Streamable HTTP/WebSocket could route around the relay entirely.** If ACP standardizes a remote transport, then a cloud-hosted agent with an `/acp` endpoint plus a browser-side ACP client is "attach your own remote agent" without any of AgentPort's protocol — and the SDK ecosystem (Rust, TypeScript, Python) will supply the clients. What that path does not give anyone is consent at the key, an ownership cert, a scoped grant, or content the transport operator cannot read; but a shipped mediocre answer beats an unshipped good one, and the RFD's own Phase 4 list shows those gaps are known and merely queued. Defence: do not compete with the transport. Be the layer above it — the wallet, the grant, the sealing, the cert — and be there while the RFD is still Active rather than after it ships.
- **Four venues are pouring the concrete for agent identity and delegation, and AgentPort is at none of them.** MCP, goose and AGENTS.md sit under the Linux Foundation's Agentic AI Foundation with eight platinum sponsors; WebMCP is in the W3C Web ML CG; Web Bot Auth has a chartered IETF WG; AP2 and Verifiable Intent went to FIDO in May 2026; and there are now at least four W3C CGs on agent identity, trust and registries. A hand-rolled `AgentCert` and `SessionDelegation` risk being the one non-standard artifact in a stack where everything else is a foundation project — which is fatal for something whose stated end state is "it stops needing a project". Defence: express the ownership model in the formats those venues are producing, and show up where the delegation semantics are being decided.
- **WebMCP itself is still a bet.** It is a Community Group draft, not on the standards track, in an origin trial, with one implementer; Edge is behind a flag and Firefox and Safari have made no implementation commitment. Origin trials expire. If Chrome narrows or withdraws it, the tool-supply story that arrived in August 2026 evaporates and AgentPort's declared-tool path reverts to sites hand-writing `SiteTool`s — the adoption problem requirement 6 already names as the one most likely to kill this. Defence: keep the harness path genuinely good rather than treating it as the fallback, and keep `SiteTool` independent enough that the harvester is a plug-in and not the foundation.
- **The scarce resource is demand, not supply, and the window is short.** As of July 2026 no mainstream agent consumed WebMCP tools; by August two large platforms had turned supply on by default. That gap will be filled by whoever is first to consume at scale, and Google has already said Gemini in Chrome will be the first mainstream consumer, with Cloudflare's own BrowserRun able to invoke the tools it injects. If the answer to "whose agent calls these tools" settles as "the browser's" or "the edge provider's" before a user-supplied option is visible, the inversion AgentPort exists to make stops being an open question. This is a distribution race, not an engineering one — which is why the unlisted extension is the most expensive open item in the repo.
- **Default-on tool supply is also default-on injection surface.** Millions of pages now emit site-authored (or edge-injected) tool names, descriptions and form annotations aimed straight at agents, and Chrome's own docs already scope WebMCP to human-supervised local workflows for this reason. AgentPort points a user's real agent — with the user's files, memory, MCP servers and other attachments behind it — at that surface. Every harvested string is untrusted, every `readOnlyHint` is a page's opinion about whether it needs approval, and a single gating bypass turns the product's core promise inside out. The existing `display()` discipline and the refusal to let a site answer its own approval are the defence, and they only hold if the harvester never grows a fast path.
