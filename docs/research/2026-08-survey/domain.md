# Domain model and DDD — do the entities own their rules?

> One of six independent reports from the 2026-08-20 survey. The findings are
> **frozen** — they describe the tree at `f7c8ee6`, and are not rewritten to
> flatter what shipped. The citations are NOT exempt from
> `npm run docs:check`: where a symbol has since moved, the citation is
> re-pointed at its current home and the original name kept in the prose, so
> the record stays true and the gate stays honest. What became of each
> finding is in `docs/research/README.md`.

# SUMMARY
AgentPort's protocol layer models its entities well as *shapes* (`messages.ts` schemas with inferred types, `refined()` invariants on `CapabilityGrant`) but almost none of them own their *rules*: the rules live as inline boolean conjunctions and switch arms inside four host classes, and where an entity is judged by more than one party, the judgement is copy-pasted rather than shared. The clearest case is `SessionDelegation` — three independent hand-written validity conjunctions in `packages/relay/src/core.ts`, `packages/daemon/src/daemon.ts` and `site/src/connect.ts`, already visibly drifted (a dead clause the schema makes unreachable; a hand-rolled regex re-implementation of an exported validator; nobody checking `issuedAt` against the clock). The repo already contains three proofs that extraction works here — `packages/daemon/src/revocations.ts` (type + rule + port + two adapters, all pure), `packages/extension/src/lifecycle.ts` (consent rules pulled out of the service worker and asserted ~20 times in `packages/extension/check.ts`), and `packages/client/src/webmcp.ts` ("one artifact for one belief") — so the recommendation is to keep applying that pattern, not to invent one. On the four big files: `daemon.ts` and `wallet.ts` are cohesive aggregates carrying one or two clearly separable non-domain services (relay transport, wire-bounding, frame correlation) and should NOT be split along session lines; `sw.ts` is a cohesive session registry with two unrelated services bolted on (consent windows, popup API); `content.ts` is genuinely two programs, and its widget half is an 11-variable module-scope state machine that deserves to be an object. A rich `AttachmentAuthority` would close a real gap rather than merely tidy: invariant 2's four enforcement points are honoured, but revocation of a *live* attachment is not part of `#authorityError` at all — it depends on a `setInterval` in `cli.ts`.

## [P0/M] SessionDelegation's validity rule is written three times, in three packages, and has already drifted
`SessionDelegation` is a bare inferred type; every rule about it is an inline conjunction at a judgement site. `packages/relay/src/core.ts#openSession` checks {sig, delegate, agent, expiresAt, lifetime, grantHash}; `packages/daemon/src/daemon.ts#onSessionOpen` checks those plus {origin, revocation} in a different order and with a different failure vocabulary; `site/src/connect.ts` (the `onMessage` handler inside `requestHostedDelegation`) checks a third set by hand-rolled regex (`/^[0-9a-f]{128}$/` on `sig`, `Number.isFinite` on `expiresAt`) rather than calling the exported `SessionDelegation` validator that already encodes exactly those shapes. Drift is visible today: the daemon still carries a `typeof delegation.origin !== 'string'` clause that `decodeFrame` makes unreachable (origin is a required `display(1, MAX_ORIGIN_CHARS)` field), and NO judge compares `issuedAt` to the current clock — only `delegationLifetimeOk` (a span check) and `expiresAt > now`. Since `isRevoked` refuses delegations with `issuedAt <= tombstone.at`, a future-dated `issuedAt` (wallet clock skew, or a page that holds the user key in the in-page demo) survives a revocation recorded now, for up to MAX_DELEGATION_LIFETIME_MS. Three copies means the missing clause has to be noticed three times.
EVIDENCE: packages/relay/src/core.ts#openSession; packages/daemon/src/daemon.ts#onSessionOpen; site/src/connect.ts#requestHostedDelegation; packages/protocol/src/messages.ts#SessionDelegation, #delegationLifetimeOk; packages/protocol/src/crypto.ts#verifyDelegation; packages/daemon/src/revocations.ts#isRevoked
RECOMMENDATION: Add `packages/protocol/src/delegation.ts` exporting one predicate — `delegationAuthorizes(delegation, {owner, agent, delegate, origin, grant, now})` returning `undefined` or a reason from a closed set ('sig'|'delegate'|'agent'|'origin'|'grant'|'lifetime'|'expired'|'not_yet_valid'). Make `origin` explicitly optional with the documented meaning "this judge cannot see a browser origin", which is the relay's real position, so the relay's weaker check is a stated parameter instead of a silently shorter conjunction. Callers: relay/src/core.ts#openSession, daemon/src/daemon.ts#onSessionOpen (which then adds only `isRevoked`), and site/src/connect.ts (which drops its regexes for `SessionDelegation(value, 'delegation')` plus the same predicate). Add `issuedAt <= now + skew` inside the predicate. It is browser-safe and dependency-free, so it ships in connect.js like `hashGrant` and `delegationLifetimeOk` already do. Assert it directly in scripts/wire-check.ts, where clause-level cases are cheap; today the only coverage is scripts/e2e.ts over real sockets.

## [P1/M] Attachment authority is a bare {grant, delegation} tuple judged by a host method — and live revocation is not one of its checks
`AgentDaemon#authorityError` takes `Pick<SessionState,'grant'|'delegation'>` and enforces the min-of-two-expiries boundary at the four points AGENTS.md invariant 2 names. But it does not consult the revocation store, and `AgentDaemon#enforceRevocations` — which ends attachments a tombstone already covers (ADR-022 R11) — is never called by the daemon itself. Its only caller is a `setInterval(..., 200)` in `packages/daemon/src/cli.ts`. So the live-session half of revocation is a CALLER OBLIGATION, not a property of the aggregate: any embedder that constructs `AgentDaemon` with a `revocations` store and no poll (scripts/e2e.ts, a service host, a future GUI) gets tombstones honoured at open and resume and never during live traffic, while `revocations()` and `enforceRevocations()` on the public surface make it look handled. Tool membership is likewise a separate lookup (`session.tools.find(...)` inside `#callTool`) rather than something the authority object answers, so 'may this attachment do X right now' has three unrelated spellings.
EVIDENCE: packages/daemon/src/daemon.ts#authorityError, #callTool, #onPrompt, #enforceRevocations, #revoke; packages/daemon/src/cli.ts (the pairingControlTimer interval); packages/daemon/src/revocations.ts#isRevoked, #RevocationStore
RECOMMENDATION: Add `packages/daemon/src/authority.ts` with an `AttachmentAuthority` value object built once in `#onSessionOpen` from `{grant, delegation, revocations}`: `expiresAt` (the min, computed once instead of re-derived), `error(now)` covering expiry AND revocation, and `allows(toolName)`. `#authorityError` becomes `session.authority.error(this.#now())` and `#callTool`'s membership lookup becomes `session.authority.allows(name)`. Move the live sweep into the daemon's existing heartbeat interval (it already expires detached sessions and stale offer seals there) so `enforceRevocations` stops being something a caller must remember; keep the public method for the CLI's idempotent nudge. Watch the cost: `fileRevocations.list()` re-reads the file per call, so consult it at prompt admission and tool dispatch and memoise per tick rather than on the late-tool-result path. Revert the sweep and watch a live session survive a tombstone in e2e — that failure has no check today.

## [P1/S] "Is this tool gated?" is a CapabilityGrant rule spelled out in seven files, two of which draw consent screens
`tool.requiresApproval || grant.alwaysAsk.includes(name)` appears in `packages/daemon/src/daemon.ts#callTool` (twice — once as the gate, once as a log field), `packages/client/src/session.ts#onToolCall`, `packages/extension/src/consent.ts`, `packages/daemon/src/cli.ts`, `packages/daemon/src/connect-cli.ts`, `wallet/src/app.ts` (the `toolRows` computed), and `examples/inkwell/src/app.ts`. `CapabilityGrant` already carries its structural invariants inside the schema (`refined()`: unique names, alwaysAsk a subset, aggregate size) — proof the project is willing to put grant rules in the grant — but the one rule a human reads before deciding lives at every call site instead. Four of the seven copies render the consent surface, so a divergence there under-warns: the daemon's terminal screen and the wallet's tool list would say a tool is free while the enforcing edge asks. The two daemon copies also differ cosmetically (`tool.requiresApproval` vs `=== true`), which is the shape drift takes before it becomes semantic.
EVIDENCE: packages/daemon/src/daemon.ts#callTool; packages/client/src/session.ts#onToolCall; packages/extension/src/consent.ts; packages/daemon/src/cli.ts; packages/daemon/src/connect-cli.ts; wallet/src/app.ts; packages/protocol/src/messages.ts#CapabilityGrant
RECOMMENDATION: Export `isGated(grant, toolName)` and `grantedTool(grant, name)` from a new `packages/protocol/src/grant.ts` (or beside `CapabilityGrant` in messages.ts), and replace all seven call sites in the same change — no wrapper left behind. Move `buildGrant`/`explainGrantViolation` out of `packages/client/src/wallet.ts` into that module too: they are the developer-facing grant constructor and have nothing to do with sockets. Add fixture cases to scripts/wire-check.ts for the gate (a tool gated only by `alwaysAsk`, one gated only by `requiresApproval`, one by both), which is checkable for the first time once the rule is a function.

## [P1/L] content.ts is two programs sharing a file, and the widget half is an eleven-variable module-scope state machine
The file's own divider comment ("Job 2 — the fallback surface") marks the seam. Above it: the mediator — page postMessage boundary, worker port, `records`/`pageCalls`/`waiters`, tool routing. Below it: the widget presenter, roughly 600 lines holding `overlayInstance`, `overlaySuppressed`, `widgetSurfaceAlive`, `widgetRef`, `widgetPromptId`, `widgetAttaching`, `widgetToolSeq`, `widgetLiveSinceBind`, `widgetTextMessages`, `widgetReasoningMessages`, `widgetPlan`, `widgetVerify` as module-level mutable state, with invariants maintained by convention across `overlay`, `attachWidget`, `reclaimWidget`, `rehydrateWidget`, `sendFromWidget`, `onWidgetEvent`, `onWidgetPlan`, `onWidgetReattached`, `onWidgetClosed`, `showWidgetAttached`. The comments document the hazards that arise from exactly this arrangement — a plan arriving for a turn this document is not running, a `reattached` landing before any panel exists, a history replay racing live output — each handled by another cross-check against another module variable. None of it is reachable from a test without a real page: `scripts/extension-ui-smoke.ts` drives it through Chrome, and nothing exercises the state machine directly.
EVIDENCE: packages/extension/src/content.ts (the `widget*` module bindings and `overlay`, `attachWidget`, `reclaimWidget`, `rehydrateWidget`, `sendFromWidget`, `onWidgetEvent`, `onWidgetPlan`, `onWidgetReattached`, `onWidgetClosed`, `showWidgetAttached`); packages/extension/src/lifecycle.ts as the precedent; packages/extension/check.ts
RECOMMENDATION: Split into `packages/extension/src/widget.ts` exporting a `WidgetSurface` class that owns ref/promptId/plan/verify/liveSinceBind/message sets and takes an `OverlayBridge` plus a `tell`/`request` pair in its constructor, leaving `content.ts` as the mediator (page boundary, worker port, `records`, `runToolCall`) that instantiates one. The immediate payoff is the same one `lifecycle.ts` bought: the transitions the comments warn about (plan for an unknown turn, reattach with no panel, replay vs live output) become assertable in `packages/extension/check.ts` with a stub bridge, instead of only in a browser smoke test. Do not also split the mediator — its three maps and the page validator are one boundary.

## [P2/S] The "which resume denials are terminal" rule is a duplicated string set over a free-text wire field
`site/src/connect.ts` (the provider's `resume`) and `packages/extension/src/sw.ts#resumeFromStore` each hard-code the same literal set — `not_resumable`, `grant_expired`, `authorization_expired`, `revoked` — to decide whether to delete a durable resume record or keep it for retry. AGENTS.md invariant 9 requires both to behave identically ("revoked is terminal for page and extension resume records; both clear the dead record"), and they do so purely by copy-paste. The producing side has no closed vocabulary to copy from: `SessionDenied.reason` is `display(0, MAX_REASON_CHARS)`, so `packages/daemon/src/daemon.ts#onSessionResume` emits these as free text and `packages/relay/src/core.ts` emits a partly different set (`agent_offline`, `duplicate_session`). This is AGENTS.md's own rule 4 ("beware string keys") pointed at production code: add a terminal reason on the daemon side and both consumers silently classify it as transient and retry a dead record forever, with nothing red.
EVIDENCE: site/src/connect.ts (provider `resume`); packages/extension/src/sw.ts#resumeFromStore; packages/client/src/wallet.ts#ResumeError, #attemptResume; packages/daemon/src/daemon.ts#onSessionResume; packages/protocol/src/messages.ts#SessionDenied
RECOMMENDATION: Put the vocabulary in the protocol: a `SESSION_DENIAL_REASONS` const object the daemon and relay emit FROM (so a new reason is a new entry, not a new literal) and `isTerminalResumeDenial(reason)` that both consumers call. That much needs no wire change and can land now. Narrowing `SessionDenied.reason` from `display` to `en(...)` is the stronger fix but is a lockstep protocol change — flag it as a v7 candidate rather than doing it incidentally. Add the exhaustiveness assertion where the other registries live (`scripts/wire-check.ts`), and delete one entry once to watch it fail.

## [P2/M] AttachmentPolicy is still a record of two booleans whose justification names a route it does not own
`attachmentPolicy({decisions, questions})` maps two booleans onto two differently-named booleans; the routing that justifies them lives elsewhere, in `AgentDaemon#requestApproval` and `AgentDaemon#ask`, each re-deriving the same `viaConnect` fork. The daemon's own comment on `#trustedSurfaces` states the general rule this violates: "a policy whose justification names a destination must be produced by the same code that routes there, or asserted by a check that observes where the frame went", and notes that a check reading `policy.mayAsk` "passes just as happily on a daemon that hands the question to the requesting site". The current code satisfies the rule only by both halves consulting `this.#options.onLocalApproval`/`onLocalAsk` independently — a convention, restated in three places (`#trustedSurfaces`, `#requestApproval`'s second lock, `#ask`'s second lock), which is exactly the arrangement that let the single-boolean bug live in a comment for as long as it did.
EVIDENCE: packages/daemon/src/runtime.ts#attachmentPolicy, #AttachmentPolicy; packages/daemon/src/daemon.ts#trustedSurfaces, #requestApproval, #ask; packages/daemon/src/runtimes/acp.ts (the `policy.mayAsk` elicitation declaration)
RECOMMENDATION: Build ONE object at `#onSessionOpen` — an `AttachmentConsent` with `askUser?: (q) => Promise<AskAnswers|undefined>` and `decide?: (domain, summary, call) => Promise<boolean>` already bound to the tier's real destination, and derive `mayAsk = askUser !== undefined`, `mayUseOwnTools = decide !== undefined` from it rather than asserting them alongside. `#requestApproval`/`#ask` then call `session.consent.decide`/`askUser` with no tier fork left to disagree with the declaration, and `AttachmentPolicy` becomes a projection of it for the runtime and the wire. Replace, do not add: the current fork must be deleted in the same change (tenet: no parallel paths). Keep `AttachmentPolicy` as the wire/runtime-facing shape so ADR-024 R5's policy channel is untouched.

## [P2/M] sw.ts is a cohesive session registry with two unrelated services bolted on — split those two, keep the registry whole
Judgement: partial decomposition, not a god-file teardown. The session registry (`SessionEntry`, `orphanSession`, `reclaimSession`, `dropSession`, `noteDocument`, `wireSession`, `openSession`, `resumeFromStore`, `dispatchToolCall`, `awaitRebind`, the content port handler) IS one aggregate and splitting it would scatter the reclaim/orphan/drop invariants that currently sit within reading distance of each other — worse than the size. But two things in the file share nothing with it. The consent-window service (`PendingUi`, `pendingUi`, `settleUi`, `openUiWindow`, the `chrome.windows.onRemoved` listener, `askConnect`, `askPair`, `askApproval`, `askQuestion`, `handleConsent`) has its own state, its own deadline (`ASK_WINDOW_MS` reasoned against the daemon's `ASK_TIMEOUT_MS`) and its own fail-closed invariant ("closing the window without answering is a denial"), and touches sessions only through one line in `dropSession`. The popup API (`onPopupMessage`, `pairOffers`, `handlePopup`) is identity/relay/pairing/agent-listing and never touches a session at all.
EVIDENCE: packages/extension/src/sw.ts#PendingUi, #settleUi, #openUiWindow, #askConnect, #askPair, #askApproval, #askQuestion, #handleConsent, #onPopupMessage, #handlePopup, #SessionEntry, #reclaimSession, #orphanSession, #dropSession, #wireSession; packages/extension/src/lifecycle.ts (the same seam already taken once)
RECOMMENDATION: Extract `packages/extension/src/consent-windows.ts` (the pendingUi service, exporting `askConnect/askPair/askApproval/askQuestion/handleConsent` plus a `closeFor(ref)` that `dropSession` calls) and `packages/extension/src/popup-api.ts` (`onPopupMessage` + `pairOffers` + `handlePopup`). `sw.ts` keeps the registry and the content port and drops to roughly 800 lines of one aggregate. State explicitly in the module header that the registry is NOT to be split further, with the reason, so the next size-driven refactor does not scatter it.

## [P2/M] daemon.ts is one legitimate aggregate carrying a relay client and a wire-bounding library that share nothing with it
Judgement: the session aggregate should stay in one file — `SessionState` plus open/resume/close/prompt/tool/approval/ask is genuinely one thing, and splitting it across modules would put invariant 2's enforcement points in four files. Two passengers are separable with no scattering. (1) Transport: `#dial`, the ping/pong heartbeat, backoff and redial, `HANDSHAKE_TIMEOUT_MS`/`#failStart`/`#readyDeferred`, `#send`, and the decode-and-drop error handling touch nothing but the socket, and `packages/client/src/wallet.ts` runs a near-parallel implementation of the same lifecycle. (2) Wire bounding: `#bounded`, `#streamText` (including the surrogate-pair split), `#boundedHistory` and `HISTORY_BUDGET_CHARS` are pure functions over `packages/protocol/src/limits.ts` values with real edge logic — timestamp-domain coercion to 0, a per-frame char budget derived from `MAX_SEALED_PLAINTEXT_BYTES`, newest-first retention — and today they are reachable only by standing up a daemon and a socket, so none of them has a direct case anywhere.
EVIDENCE: packages/daemon/src/daemon.ts#dial, #failStart, #send, #bounded, #streamText, #boundedHistory (HISTORY_BUDGET_CHARS); packages/protocol/src/limits.ts; packages/client/src/wallet.ts#dial, #scheduleReconnect
RECOMMENDATION: Extract `packages/daemon/src/relay-link.ts` (a `RelayLink` owning dial/heartbeat/backoff/handshake deadline, emitting decoded frames and a close event) and `packages/daemon/src/bounds.ts` (`boundedString`, `chunkText`, `boundedHistory`). Add cases for the bounding functions to `scripts/wire-check.ts`, where every other bound already lives — a surrogate pair straddling `MAX_TEXT_CHARS`, an entry list that exceeds the char budget before the entry cap, an out-of-domain timestamp. Do not try to unify `RelayLink` with the wallet's dial loop in the same change: the wallet's reconnect also re-resumes sessions, and merging them would create the cross-package abstraction the daemon does not need.

## [P2/S] wallet.ts hides a general request/response multiplexer — with a hand-maintained set and a known past bug — inside the wallet class
`#await`, `#awaitTimed`, `#request`, `#resolve` and `DENIAL_ANSWERS` are a frame-correlation registry that knows nothing about wallets, keys, or sessions. Its comments record two real defects it now guards against: a deferred registered under two types leaving a stale twin that starved every waiter behind it, and a refusal frame nobody listed leaving the caller hanging. Both are properties of the multiplexer alone, and neither can be exercised today without a wallet, a socket and a relay. `DENIAL_ANSWERS` is explicitly documented as a hand-maintained set that "cannot be made total" — precisely the kind of registry AGENTS.md says will eventually be wrong — and it sits next to the sealing, pairing, connect and resume flows rather than anywhere a targeted check could reach it.
EVIDENCE: packages/client/src/wallet.ts#await, #awaitTimed, #request, #resolve, DENIAL_ANSWERS, #establishSeal, #makeSession
RECOMMENDATION: Extract `packages/client/src/correlator.ts` with a `FrameCorrelator` (register/cancel/resolve, the timed variant, and the denial backstop table) taking only a `Logger`. Then assert directly, with no socket: a two-type waiter withdraws both entries on settle; a timeout withdraws its waiter so a late reply cannot be swallowed; an unlisted `session.denied` fails the oldest plausible request and logs. Keep the seal-establishment and the four flows in `AgentWallet` — those are the aggregate. Pair this with moving `buildGrant`/`explainGrantViolation` to the grant module (finding 3), which leaves wallet.ts at roughly 750 lines of flow.

## [P2/S] The extension redefines five protocol bounds as its own LIMITS, in a file that already imports protocol bounds
`packages/extension/src/bridge.ts` declares `LIMITS = {tools: 64, toolNameLength: 128, descriptionLength: 4096, textLength: 131072, jsonBytes: ...}`, which shadow `MAX_TOOLS_PER_GRANT` (64), `TOOL_NAME_PATTERN` (1–128), `MAX_DESCRIPTION_CHARS` (4096) and `MAX_TEXT_CHARS` (131_072) — numerically identical today, related by nothing tomorrow. The same file already imports `MAX_PLAN_STEPS`, `MAX_PLAN_STEP_CHARS`, `MAX_FORM_FIELDS`, `MAX_ANSWER_CHARS` and `ID_PATTERN` from the protocol and says so in `sanitizePlanSteps`'s comment ("an answer that would survive this hop and then be refused by the daemon's decoder is a boundary that lies about what it accepts") — the tool path just never got the same treatment. `sanitizeToolDefinition` also re-implements `TOOL_NAME_PATTERN` as a local regex plus a length check. AGENTS.md is explicit: "Change a limit here, not at a call site."
EVIDENCE: packages/extension/src/bridge.ts#LIMITS, #sanitizeToolDefinition, #sanitizeTools, #sanitizePlanSteps; packages/protocol/src/limits.ts#MAX_TOOLS_PER_GRANT, #TOOL_NAME_PATTERN, #MAX_DESCRIPTION_CHARS, #MAX_TEXT_CHARS
RECOMMENDATION: Derive the shadowing members of `LIMITS` from the protocol constants (`tools: MAX_TOOLS_PER_GRANT`, `descriptionLength: MAX_DESCRIPTION_CHARS`, `textLength: MAX_TEXT_CHARS`) and use `TOOL_NAME_PATTERN` in `sanitizeToolDefinition`; keep only the genuinely extension-local bounds (`sessionsPerChannel`, `pendingCallsPerSession`, `jsonBytes`) with the reasoning that chose them. Add one assertion in `packages/extension/check.ts` that a tool name the protocol accepts survives the sanitizer and one the protocol rejects does not — the boundary either agrees with the wire or it lies about what it accepts, and right now nothing says which.

## [P3/S] Four per-tier attachment aggregates is right; four re-derivations of what the page may learn is not
`SessionState` (daemon), `AgentSession` (client), `SessionEntry` (extension worker) and `SessionRecord` (content script) are legitimately different aggregates — each holds state the others must not — and merging them would be a mistake. What is duplicated is the DISCLOSURE rule. `packages/extension/src/sw.ts#infoFor` decides per-tier which of `{agentName, runtime, verify, ownTools, alias}` a page may see, with a paragraph of ADR-009 reasoning; `packages/extension/src/content.ts` re-applies the same widget-vs-page split when forwarding `reattached` (`current?.from === 'widget' ? payload : {}`); `packages/daemon/src/daemon.ts` independently substitutes 'Personal agent' for a delegated attachment in two places (open and resume — and the resume copy is documented as having once derived it twice and got it wrong, breaking every delegated resume). The rule "a delegated or page-tier surface learns a generic label and nothing about the attachment's keys" is therefore stated four times in three packages.
EVIDENCE: packages/extension/src/sw.ts#infoFor, #wireSession (the `reattached` forward); packages/extension/src/content.ts#onWidgetReattached; packages/daemon/src/daemon.ts#onSessionOpen, #onSessionResume (responseAgentName / resumedAgentName); packages/client/src/session.ts#SessionInfo
RECOMMENDATION: Low-risk, high-clarity: give the extension one `visibleInfo(entry)` used by both `infoFor` and the `reattached` forward, so the widget/page fork exists once; and in the daemon, derive the outward-facing label once per session (store it on `SessionState` at open, restate it on resume) instead of computing it at each answer site — the comment in `#onSessionResume` already records what the second derivation cost. Do not attempt to unify the four aggregates themselves; per-tier state is the boundary, and collapsing it would put daemon-only fields in reach of the page tier.
