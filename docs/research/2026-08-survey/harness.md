# The generic page harness, and what distribution will be asked

> One of six independent reports from the 2026-08-20 survey. The findings are
> **frozen** — they describe the tree at `f7c8ee6`, and are not rewritten to
> flatter what shipped. The citations are NOT exempt from
> `npm run docs:check`: where a symbol has since moved, the citation is
> re-pointed at its current home and the original name kept in the prose, so
> the record stays true and the gate stays honest. What became of each
> finding is in `docs/research/README.md`.

# SUMMARY
The generic harness is seven tools — `page.info`, `page.readText`, `page.readSelection`, `page.listElements`, `page.scroll`, `page.fill`, `page.click` (`packages/extension/src/pagetools.ts#genericPageTools`) — and its read boundary is genuinely good: visibility is conservative, truncation and hidden-block counts are reported, handles refuse to resolve when an element's role or label moved. What is missing is everything that turns reading into driving. There is no navigate, no wait-until, no find-by-text, no select/checkbox/keypress; `document.querySelectorAll` and a `document.body` TreeWalker mean shadow DOM and every iframe are invisible, so a large class of modern sites reads as an empty page; and `obstruction()` returns "no obstruction" both when the element is clear and when it could not look (anything outside the viewport), so silence means permission on the one check standing between a borrowed agent and the wrong button. The deeper problem is the consent surface rather than the tools: the approval card renders `Run page.click` plus `{"element":"g3e12"}` (`packages/extension/src/consent.ts#Approve`, `packages/client/src/session.ts#AgentSession` summary), so every mutation on an undeclared site is approved blind — and it never times out. On the two north-star demands: navigation survival is genuinely built for the widget tier and works within an origin (`lifecycle.ts#reclaimKeyFor`, `sw.ts#reclaimSession`, `sw.ts#resumeFromStore`), but crossing an origin destroys the ACP session and the conversation with it, and the page tier's reclaim key omits the tab entirely. Remembered consent has no store, no surface, and — critically — no kill switch: ADR-022's tombstone is keyed on `SessionDelegation` and the extension is a direct-key tier, so `agentport revoke <origin>` neither closes nor blocks an extension attachment today. Distribution is one manifest review away from being asked hard questions about a content script and `navigator.agent` shim that announce themselves on every page on the web before any user consent.

## [P0/M] The approval card cannot name what the agent is about to click
Per-call approval is the entire safety story for the generic harness — ADR-021 §3 refuses to remember mutations precisely because each one must be judged individually. But the card the user judges says almost nothing. The summary is hardcoded `Run ${frame.name}` in `packages/client/src/session.ts#AgentSession` (`#onToolCall`), and the arguments are rendered as raw JSON by `packages/extension/src/consent.ts#Approve`, so a click approval reads: authority line, "Personal agent asks: Run page.click", `{"element":"g3e12"}`. The handle is an opaque generation counter. The user is being asked to authorise an irreversible action against a token they cannot evaluate, on a page whose text the agent has been reading — which is the exact combination ADR-021 §6 names as the hard problem. The information exists: `packages/extension/src/pagetools.ts#Handle` already stores the element's `role` and `name` as they were when listed, and `resolveHandle` already compares against them. The deleted `describeCall()` comment in `pagetools.ts` documents why it was not wired up (the description must be computed where the DOM is, the card renders in extension origin, so it is a round trip and a message type) and explicitly says it is worth building. Nothing has been built since. Training users to approve an unreadable dialog every few seconds is worse than not asking — it manufactures the reflexive-approval habit the ADR says is the worst possible outcome.
EVIDENCE: packages/extension/src/consent.ts#Approve; packages/client/src/session.ts#AgentSession (#onToolCall builds `summary: `Run ${frame.name}``); packages/extension/src/pagetools.ts#Handle; packages/extension/src/pagetools.ts#resolveHandle; the deleted-describeCall comment block above packages/extension/src/pagetools.ts#genericPageTools
RECOMMENDATION: Add a `describe` request to `ContentToWorker` in packages/extension/src/bridge.ts; export a `describeHandle(handle)` from pagetools.ts returning `{role, name, obstructed?}` (never the field VALUE, per the existing no-values rule); have `packages/extension/src/sw.ts#askApproval` await it before opening the window and carry it on `ConsentPayload`; render it in consent.ts#Approve above the JSON, and render a distinct line when the description could not be produced because `resolveHandle` now refuses (that refusal is the most important thing the card can say). The round trip must be bounded and must fail toward "I cannot name this target — decline", matching the `never` default already in consent.ts#Approve.

## [P0/M] `agentport revoke` does not reach an extension attachment at all
ADR-022 makes the revocation object a `SessionDelegation` addressed by origin. The extension tier issues no delegation — its service worker holds the user key and opens direct-key sessions (`packages/extension/src/sw.ts#openSession` via `AgentWallet#openSession`). Every revocation check in the daemon is inside a delegation guard: `packages/daemon/src/daemon.ts#enforceRevocations` filters `session.delegation && isRevoked(...)`, the resume path checks `isRevoked` only within `if (session.delegation)`, and the open path checks it only within `if (frame.delegation)`. The CLI path writes the tombstone durably and does not talk to the process; the control poll then calls `enforceRevocations`, which skips every extension session. The in-process `packages/daemon/src/daemon.ts#revoke` does close by `session.surface.origin`, but it is reachable only from the owner-key `revoke` frame, which the extension has no UI to send. Net effect: a user who installs the extension, attaches on a site, then runs `agentport revoke https://that-site` gets a tombstone, a log line, and a live attachment that continues and can reopen. That is a false security guarantee on north-star requirement 4, and it is the load-bearing prerequisite for remembered consent — you cannot make consent durable before you can take it back.
EVIDENCE: packages/daemon/src/daemon.ts#enforceRevocations (filters on `session.delegation`); packages/daemon/src/daemon.ts#revoke; the `if (session.delegation)` guard in packages/daemon/src/daemon.ts#onSessionResume and the `if (frame.delegation)` guard in the open path; packages/extension/src/sw.ts#openSession (no delegation); docs/ADR-022-revocation.md
RECOMMENDATION: Make the tombstone address the ORIGIN of the attachment, not the delegation that authorised it. In packages/daemon/src/revocations.ts and daemon.ts, judge `session.surface.origin` (with `session.delegation` still checked for the delegated tier's issued-at semantics) in `enforceRevocations`, the resume path, and the open path — a tombstone `{origin, at}` should refuse any session opened on that origin at or before `at`, whatever tier authorised it. Add the adversarial e2e case in the same change (extension-shaped direct-key session, tombstone written by the CLI path, assert both close and refused reopen), because the current suite's scope was drawn around delegations and passes today without ever mentioning the direct-key tier — AGENTS.md rule 5b exactly.

## [P1/S] An unanswered approval window blocks the agent's turn forever
`packages/extension/src/sw.ts#askQuestion` has `ASK_WINDOW_MS` (4 minutes, deliberately inside the daemon's `ASK_TIMEOUT_MS`) and explains why: past the daemon's own deadline the user would fill in a form that goes nowhere. `packages/extension/src/sw.ts#askApproval` has no timer at all. On the daemon side the asymmetry is the same — `#ask` arms a timer with `ASK_TIMEOUT_MS`, `packages/daemon/src/daemon.ts#requestApproval` arms only an abort listener. Closing the window resolves false via `chrome.windows.onRemoved`, but a window left open on another virtual desktop, or a worker evicted with the window still up, leaves the ACP turn parked indefinitely — the daemon has no tool-call timeout, which `sw.ts` itself notes twice as the reason `NAV_SETTLE_MS` and the content script's `TOOL_CALL_TIMEOUT_MS` exist. This is AGENTS.md check-rule 3 ("never hang") applied to the product rather than to a check, and ADR-025 R5 already states the requirement: "Approval gets a deadline as elicitation already does; neither path may wait forever." On the harness, where a flow is a dozen gated calls, one forgotten window wedges the agent silently.
EVIDENCE: packages/extension/src/sw.ts#askApproval versus packages/extension/src/sw.ts#askQuestion (ASK_WINDOW_MS); packages/daemon/src/daemon.ts#requestApproval versus the ASK_TIMEOUT_MS timer in the `#ask` path; docs/ADR-025-custody-safe-client-boundary.md R5
RECOMMENDATION: Arm a deadline in `sw.ts#askApproval` mirroring `askQuestion` (settle to a decline, close the window, log it), and independently arm one in `packages/daemon/src/daemon.ts#requestApproval` so the daemon does not depend on a client honouring its own — the daemon is the party whose turn is blocked. Both deadlines are a decline, never a grant. Add the e2e case that opens an approval and never answers, asserting the turn ends within the deadline rather than the harness hanging (a hang is indistinguishable from slowness, which is why this check has to exist rather than be assumed).

## [P1/L] The harness cannot see shadow DOM or any iframe, and says the page is empty rather than saying it cannot see
`packages/extension/src/pagetools.ts#listElements` calls `document.querySelectorAll(selector)` and `visibleText()` walks `document.body` with a TreeWalker. Neither pierces a shadow root, open or closed. Any site built on web components — and that includes a large share of enterprise apps, several major consumer sites' player and comment surfaces, and most design-system-based checkout flows — returns zero interactive elements and a fraction of its text. Iframes are the same story from the other direction: the content script does run in all frames (`all_frames: true` in the manifest), but the widget and its tool handlers exist only in the top frame (`if (window.top === window)` at the bottom of packages/extension/src/content.ts), so the handlers' `document` is the top document only. Every embedded checkout, OAuth consent, payment field, help widget and video player is invisible. The failure is silent and indistinguishable from an empty page: `page.readText` returns `{text: '', truncated: false, hiddenBlocks: 0}` and `page.listElements` returns `{elements: [], truncated: false}` — the agent concludes the page has nothing on it and acts on that. That is the same class of defect the file's own comments were written to eliminate (an agent that reads an excerpt and does not know it was an excerpt), one level up.
EVIDENCE: packages/extension/src/pagetools.ts#listElements; packages/extension/src/pagetools.ts (the `visibleText` TreeWalker over `document.body`); the `window.top === window` boot guard at the end of packages/extension/src/content.ts; `all_frames: true` in packages/extension/static/manifest.json
RECOMMENDATION: Two changes in pagetools.ts, one honest and cheap, one real. First, count what was skipped and say so: while walking, tally elements whose `shadowRoot` is non-null and `HTMLIFrameElement`s encountered, and return `shadowRoots` / `frames` counts alongside `truncated` and `hiddenBlocks` — the harness must never report an empty page when it means an unreadable one. Second, recurse into open shadow roots in both the TreeWalker's acceptNode path and `listElements`, minting handles the same way (closed roots stay unreachable and are counted). Multi-frame is the larger piece and belongs in content.ts: elect the top frame as harness owner, have subframe content scripts register with the worker, and route a handle namespaced by frame — that also needs the approval card to name the frame's origin, so it should land after the card fix above rather than before it.

## [P1/L] Four missing verbs, and each one blocks a whole class of real flow
Inventory today: `page.info`, `page.readText`, `page.readSelection`, `page.listElements`, `page.scroll` ungated; `page.fill`, `page.click` gated. What is absent and what it costs: (1) NAVIGATE — ADR-021 §2 proposes it and does not build it, so the agent can only act on the page the user happens to be on; it cannot open a link it read, cannot go back, cannot start a flow. (2) WAIT-UNTIL — `#settle` answers "has the DOM stopped moving", which ADR-021 §5 already identifies as the wrong question; there is no "wait until this appears", so on any SPA that fetches after a click the agent's only move is to re-read and hope. `page.scroll` does not even call `settle`, and uses `behavior: 'smooth'`, so an infinite-scroll read immediately after a scroll returns the pre-scroll DOM. (3) FIND — with `MAX_ELEMENTS` at 200 and enumeration in document order, a large app's listing is nav, cookie banner and footer; `truncated: true` is honest and useless, because there is no way to ask for the elements near a piece of text. (4) NON-TEXT INPUTS — `page.fill` throws `that element is not a text field` for `<select>`, and there is no checkbox/radio set and no key press, so a form with a dropdown or one that submits on Enter cannot be completed even though `listElements` cheerfully enumerates the select. These are the harness's failure modes, which the north star says are the product's failure modes.
EVIDENCE: packages/extension/src/pagetools.ts#genericPageTools (the seven-tool list; the `page.scroll` handler returns `{ok:true}` without awaiting settle); packages/extension/src/pagetools.ts#settle and MAX_ELEMENTS; docs/ADR-021-web-harness.md §2 and §5 ("Waiting. Still open, and still the one that matters most")
RECOMMENDATION: Order them by what unblocks the most flows per unit of consent risk. `page.waitFor({text|handle, timeoutMs})` and `page.find(query)` are pure reads and need no new approval semantics — add both to pagetools.ts, and make `page.scroll` await `settle()` and return `{stable, mutations}` like click does, so a scroll-then-read on an infinite list is honest. `page.select` / `page.setChecked` / `page.pressKey` are mutations and ride the existing `requiresApproval` path — but they must land AFTER the approval card can name its target, or they multiply the blind-approval problem. `page.navigate` is the one with real design left: it needs the cross-origin decision (finding on the origin boundary below), a distinct `navigation` authority domain in `packages/protocol` `AuthorityDomain` with its own sentence in consent.ts#Approve, and a rule that a navigate away from the granted origin ends the grant rather than carrying it.

## [P1/S] The obstruction check treats "I could not look" as "it is clear"
`packages/extension/src/pagetools.ts#obstruction` returns `undefined` in three different situations: the element is genuinely unobstructed; `document.elementFromPoint` is unavailable; and the element's centre point is outside the viewport, where `elementFromPoint` returns null. `page.click` treats `undefined` as permission to proceed. Nothing scrolls the target into view first, so any element below the fold — which on a long page is most of them — is clicked with the obstruction check structurally unable to fire. The check is also centre-point only, so an element covered across 90% of its area with a clear centre passes. The file's own comment says it "says nothing rather than guessing where it cannot", which is the right instinct, but the caller converts that silence into a green light. This is the same failure direction that consent.ts#Approve's `default` branch was rewritten to avoid — falling through to the least alarming answer — and here it is on the code path that decides whether a click a person could not have made gets made anyway.
EVIDENCE: packages/extension/src/pagetools.ts#obstruction; the `page.click` handler in packages/extension/src/pagetools.ts#genericPageTools (`const blocked = obstruction(el); if (blocked) throw`); packages/extension/src/pagetools.ts#isVisible (accepts elements below the fold, correctly, which is what puts them outside elementFromPoint's reach)
RECOMMENDATION: Change the return type to a three-state result in pagetools.ts — `{state: 'clear'} | {state: 'blocked', by: string} | {state: 'unknown', why: string}` — and have `page.click` scroll the element into view, await `settle()`, and re-check before acting. `unknown` must reach the approval card (it is exactly the fact the user needs) and must be reported in the tool result, not swallowed. Sample more than the centre point (corners plus centre) so partial cover is caught. The `elementFromPoint` path has never executed in any check — see the evidence-gap finding — so revert-and-watch it fail once before believing the fix.

## [P1/M] The extension announces itself on every website in the world, before any consent
`packages/extension/src/content.ts` runs at `document_start` on `http://*/*` and `https://*/*` and unconditionally calls `injectProvider()`, which loads `inpage.js`; `packages/extension/src/inpage.ts` then defines `navigator.agent` on every page and, when the browser has no WebMCP, installs a shim on both `document.modelContext` and `navigator.modelContext`. The top frame additionally renders the floating panel on every page (`overlay().show()` in the boot block of content.ts), whether or not any agent is paired. Three consequences. First, it contradicts a stated north-star property verbatim: "On an undeclared site, the site does not even know an agent is present" — every site learns the extension is installed, before consent, as a stable and globally unique fingerprinting bit. Second, the WebMCP shim changes web-platform feature detection on every site on the web; a page that branches on `document.modelContext` being present now takes a different branch because of us. Third, it is the first thing a Chrome Web Store reviewer will ask about, alongside `host_permissions: ["http://*/*", "https://*/*"]` and an `all_frames` content script — the combination that produces the "read and change all your data on all websites" install warning.
EVIDENCE: packages/extension/static/manifest.json (content_scripts matches + all_frames, host_permissions); packages/extension/src/content.ts (`injectProvider()` at boot, `overlay().show()` in the top-frame block); packages/extension/src/inpage.ts (`Object.defineProperty(target.navigator, 'agent', …)` and `installWebMcp`); docs/NORTH-STAR.md, "the site does not even know an agent is present"
RECOMMENDATION: Introduce a per-origin enablement record in packages/extension/src/storage.ts (the same store remembered consent needs, so build it once). Default off: on a non-enabled origin the content script injects nothing into page world and renders no FAB, and discovery happens through the toolbar action or the keyboard shortcut — a user gesture, which ADR-021 §3 requires anyway. Keep `navigator.agent` installation for origins the user has enabled and for pages that opt in by declaring a surface. Add `use_dynamic_url: true` to the `web_accessible_resources` entry so the extension ID is not a second stable probe. Expect to write the store listing's justification for broad host permissions and a privacy policy covering page-text egress regardless — the harness reads the whole visible document and sends it, sealed, to the user's own agent, and that has to be stated plainly rather than argued from the sealing.

## [P1/L] Remembered consent has no store, no surface, and no revocation path — here is where each belongs
Nothing is remembered today: every attach opens a connect window (`sw.ts#askConnect`), and every gated call opens an approval window (`sw.ts#askApproval`). ADR-021 §3, as corrected by the security review, is the right model and its constraints are already justified — remember ATTACHMENT and READ-ONLY observation, never mutation; scope to exact origin + agent device key + tab + top frame + document epoch + policy version; non-rolling expiry; visible and atomically revocable. The pieces needed do not exist. There is no durable per-(agent, origin) policy record — `storage.ts` has `StoredResume` (session-scoped, keyed `origin\nname`) and `StoredCert`, and nothing else. There is no origins-holding-your-agent list: `popup.ts` renders `Sessions` from the worker's in-memory table, which is live sessions, not standing authority. And the kill switch is missing at the far end, per the revocation finding above. The other blocker is upstream: ADR-021's ship order puts runtime containment (ADR-019 Gate C — scoping the agent's OWN tools per attachment) at step 3, before any remembering, and that is still unbuilt, so a poisoned page can still talk the borrowed agent into reading the user's home directory. Remembering reads without it reduces the friction protecting exactly that.
EVIDENCE: packages/extension/src/storage.ts (StoredResume, StoredCert — no policy record); packages/extension/src/sw.ts#askConnect and #askApproval; packages/extension/src/popup.ts#Sessions; docs/ADR-021-web-harness.md §3 and its ship order (steps 3, 6, 7, 8)
RECOMMENDATION: Land it in this order, and not before Gate C. (1) storage.ts gains a `StoredPolicy {origin, agent, policyVersion, issuedAt, expiresAt}` in `chrome.storage.local`, written only from the connect consent window (a new checkbox on consent.ts#Connect, off by default), covering attachment plus the five read-only tools by NAME — never a class like "reads". (2) sw.ts#openSession consults it before `askConnect` and skips the picker only on an exact match, still requiring the tab's user gesture, never activating on navigation alone. (3) popup.ts gains the standing-authority list with per-row revoke and a kill-all that clears the store AND sends the wire `revoke` for that origin — which is why the daemon-side origin-keyed tombstone is a prerequisite, not a parallel task. (4) The mutation path stays per-call, permanently, with no flag; ADR-021's conclusion that `click` is not a security class and `fill` is already egress does not weaken with better scoping.

## [P2/L] A session survives navigation within an origin but the conversation dies at the origin boundary
The widget half of "the attachment belongs to the user and the origin" is genuinely built and correct: `lifecycle.ts#reclaimKeyFor` keys a widget on `widget|origin|tabId`, `sw.ts#reclaimSession` hands a parked session to the next document, `sw.ts#resumeFromStore` recovers it after worker eviction, in-flight tool calls park in `sw.ts#awaitRebind` rather than failing, and content.ts rehydrates the transcript from the agent's own store. What is not built is the other half. A cross-origin top-level navigation runs `sw.ts#noteDocument` → `dropSession` → a real `session.close` on the wire → `packages/daemon/src/daemon.ts#closeSession` → `runtime.closeSession()`, and `packages/daemon/src/runtimes/acp.ts` states the consequence directly: "A new AgentPort attachment is a new authority boundary and therefore a new ACP session." So following a link off the origin does not merely re-scope the agent's authority — it ends the thread. Refusing to carry the GRANT across origins is right and must not change. Ending the CONVERSATION is a separate decision that was never made explicitly; it fell out of grant and thread being the same object. The runtime already supports the missing capability: `AcpRuntime#replayHistory` calls ACP `session/load` against a stored `sessionId`, so thread continuity across a re-consented attachment is reachable rather than speculative.
EVIDENCE: packages/extension/src/sw.ts#noteDocument and #dropSession; packages/extension/src/lifecycle.ts#leftBehindByNavigation; packages/daemon/src/daemon.ts#closeSession; packages/daemon/src/runtimes/acp.ts (the `session/new` comment and #replayHistory); docs/NORTH-STAR.md, "A session must outlive a navigation"
RECOMMENDATION: Separate thread identity from grant identity. Give the daemon a `threadId` distinct from the session id, minted per (user, agent) conversation and carried in `session.open` as an optional field in packages/protocol/src/messages.ts; when present and the runtime supports `loadSession`, `AcpRuntime#newSession` resumes that ACP session instead of creating one, with the NEW grant's MCP bridge — the tools change, the thread does not. In the extension, `noteDocument` then closes the grant and remembers the thread for the tab; the next origin's consent window shows "continue the same conversation on <new origin>" as an explicit, defaulted-off choice, because carrying a thread carries site A's page text into a turn running on site B and that is a prompt-injection flow the user has to authorise, not inherit. Wire fixtures and the coverage gate in scripts/fixtures/wire/ move in the same change; this is a protocol field, so relay and endpoints cut over together.

## [P2/S] Page-tier reclaim is not scoped to the tab, and any subframe is a first-class session requester
`packages/extension/src/lifecycle.ts#reclaimKeyFor` keys the widget tier on `widget|origin|tabId` and explicitly explains why the tab is in the key. The page tier is keyed `page|origin|name` with no tab component, and `lifecycle.ts#mayReclaim` compares key, origin, closed and expiry — never the tab. Meanwhile `packages/extension/src/sw.ts` accepts a content port from any frame (`handleContent` requires only `port.sender.tab`), and `injectProvider()` runs in every frame, so a cross-origin subframe can open its own session under its own origin. Combined: an attachment granted to origin X while the user was on site A, once orphaned (`orphanSession`, ORPHAN_GRACE_MS = 2 minutes), can be reclaimed by any origin-X document anywhere — including an X iframe embedded by an unrelated site B, in a different tab, with no UI and no gesture. `leftBehindByNavigation` will not evict it either, because it only considers `frameId === 0` entries. ADR-021 §3 states the intended scope as "exact HTTPS top-level origin, the selected agent device key, the tab, the top frame, the active document epoch" and "no remembered iframe authority"; the implementation is weaker than the ADR that governs it. The same subframe reachability makes the consent surface floodable: `sw.ts#openUiWindow` has no cap and `LIMITS.sessionsPerChannel` is per port, so a page with twenty iframes can spawn twenty focused OS popup windows.
EVIDENCE: packages/extension/src/lifecycle.ts#reclaimKeyFor (page branch omits tabId) and #mayReclaim; packages/extension/src/lifecycle.ts#leftBehindByNavigation (frameId === 0 only); packages/extension/src/sw.ts#handleContent and #openUiWindow; packages/extension/src/content.ts (`injectProvider()` outside the top-frame guard); docs/ADR-021-web-harness.md §3 scope list
RECOMMENDATION: Put the tab in the page-tier key in lifecycle.ts#reclaimKeyFor (`page|origin|tabId|name`) and add an explicit tab comparison to `mayReclaim` — the widget branch already documents why, and duplicating the check rather than relying on the key format is the pattern `mayReclaim` already uses for origin. Decide subframe policy deliberately: either refuse `connect`/`resume` from `port.sender.frameId !== 0` in sw.ts#handleContent, or keep it and mark the session non-reclaimable with a `reclaimKey` of null, matching how opaque origins are already handled. Add a global cap plus per-origin cooldown on `pendingUi` in sw.ts#openUiWindow, denying beyond it rather than queueing. Each of these needs its adversarial check in packages/extension/check.ts, where `mayReclaim` is already directly assertable because lifecycle.ts is Chrome-API-free.

## [P2/M] The harness's two riskiest code paths have never executed in a real browser
packages/extension/check.ts does exercise pagetools.ts — and the comment above that block is honest that nothing did until recently — but it runs under happy-dom, where it must stub `Element.prototype.getBoundingClientRect` to a fixed 100x20 box and set `checkVisibility` to `undefined`. So the primary branch of `pagetools.ts#isVisible` (the browser's own `checkVisibility({contentVisibilityAuto, opacityProperty, visibilityProperty})`) has never run, only the hand-rolled fallback; the off-canvas rect rules have never run against a real rect; and `pagetools.ts#obstruction`, which depends entirely on `document.elementFromPoint`, has never run at all. The check file says so, and points at "the Chrome smoke harness, which has one" — but scripts/extension-ui-smoke.ts asserts only iframe isolation, custom-element registry ownership, FAB layout and navigation-time host uniqueness. It never attaches an agent, never calls a page tool, never opens a consent window. So the two functions that decide what a hostile page may say to a borrowed agent, and whether a click lands where the user thinks, are covered by a harness that structurally cannot see their real behaviour — AGENTS.md rule 1 (a check nobody has watched fail) at close range.
EVIDENCE: packages/extension/check.ts, the generic-page-harness block (the `getBoundingClientRect` box stub and `checkVisibility = undefined`); packages/extension/src/pagetools.ts#isVisible and #obstruction; scripts/extension-ui-smoke.ts (checks are iframe isolation, chat registry, FAB layout, post-navigation isolation)
RECOMMENDATION: Extend scripts/extension-ui-smoke.ts — it already drives real Chrome with the unpacked extension over CDP — with a fixture page carrying white-on-white text, an `opacity:0` ancestor, an element pushed off-canvas, a full-page overlay covering a button, and a target below the fold. Assert `page.readText` excludes each hidden family and counts them; assert `page.click` refuses the covered button and NAMES the coverer; assert the below-the-fold click either scrolls-and-verifies or reports `unknown` once the obstruction fix lands. Sabotage each once (revert the `closest('[aria-hidden]')` guard, revert the obstruction throw) and read the failure to confirm it is the failure you caused, not a layout difference.

## [P2/M] Distribution: the manifest is store-shaped, the background behaviour and the listing story are not
Nothing in the code assumes load-unpacked — no hardcoded extension ID, every extension URL goes through `chrome.runtime.getURL`, the manifest carries no `key`, and packages/extension/build.ts stamps the root version (`0.0.13`, a valid Chrome version) over the `0.0.0` placeholder and strips `_build_note`. `chrome.windows.create/remove` needs no permission, and the declared `["storage", "alarms"]` are exactly what is used. What will actually generate review friction: (1) `host_permissions` for all http and https plus an `all_frames` `document_start` content script produce the maximum install warning and require a written single-purpose and minimum-permissions justification; (2) the harness reads whole-document text and transmits it off-device (sealed, to the user's own agent, but off-device), which mandates a privacy policy and an explicit limited-use disclosure in the listing; (3) `packages/extension/src/sw.ts` registers a one-minute `chrome.alarms` whose listener calls `keepAlive()` UNCONDITIONALLY — the `setInterval` beside it correctly checks `sessions.size > 0`, the alarm does not — so the service worker is woken every minute for the life of the install even with no agent paired and no session open; (4) packages/extension/build.ts sets `sourcemap: 'inline'` for all six bundles in every build, inflating the uploaded package with full sources. The README already says there is no store listing and that it is a load-unpacked build, which is the honest state; these are the items between here and a submission.
EVIDENCE: packages/extension/static/manifest.json; packages/extension/build.ts (version stamping, `sourcemap: 'inline'`); packages/extension/src/sw.ts (the `chrome.alarms.onAlarm` listener calling keepAlive unconditionally, versus the session-gated setInterval above it); README.md (the load-unpacked note)
RECOMMENDATION: Gate the alarm listener on `sessions.size > 0` in sw.ts exactly as the interval already is, and clear the alarm when the last session closes — an always-on background worker is both a battery complaint and a reviewer question. Split build.ts into dev and release configurations, keeping inline sourcemaps for dev and emitting external or no sourcemaps for the packaged upload. Write the two listing artifacts as source-controlled files beside the manifest (permission justification, privacy policy) so they are reviewed like code rather than typed into a form. Consider `optional_host_permissions` with a narrow default set if the per-origin enablement model from the announcement finding lands, since that model makes broad host access an opt-in per site rather than an install-time grant — which is both a better story for review and a better story for the user.
